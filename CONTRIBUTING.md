# Contributing to hive.support

## Verify. Correct. Evolve.

Both humans and AI agents contribute to this knowledge base — and both get things wrong. A research agent may misread a C++ template. A human may miss a hardfork guard. The KB is a living approximation that improves with every correction.

Your job as a contributor is simple: when you notice the KB disagrees with the code (or vice versa), write it down. The pipeline investigates, and the next revision gets more accurate.

## The Lifecycle

This is a **consumer repo** — a published snapshot of the Hive knowledge base. The content in `reference/` and `research/` is generated by a producer pipeline that reads Hive source code directly. You cannot edit those files here.

What you *can* do is **report errors, gaps, and inconsistencies** via `contrib/`. Your feedback gets digested into the next KB revision.

```
You find a problem
       |
       v
Write a file in contrib/hive-core/
       |
       v
Submit a merge request (or commit directly if you have access)
       |
       v
Producer pipeline reads your contribution
       |
       v
Investigates against actual source code
       |
       +-- Confirmed -> KB updated, your file archived
       +-- Refuted -> archived with explanation
```

## How to Contribute

### 1. Create a file

```
contrib/hive-core/YYYY-MM-DD-<source>-<slug>.md
```

Where `<source>` identifies who you are:
- `user` — a human contributor
- `researcher` — the hive-researcher agent
- `reviewer` — the hive-reviewer agent

Example: `contrib/hive-core/2026-04-10-user-vote-mana-edge-case.md`

### 2. Use this format

```markdown
# Short descriptive title

- **Topic**: hive-core
- **Type**: correction | addition | question | inconsistency
- **Affects**: reference/operations.md, research/hive-core/findings/04-chain-evaluators.md
- **Source**: (optional) file:line in hive-core, API response, or "observed behavior"

## Description

What you found, what's wrong, or what's missing.

## Evidence

Source code citations, test output, API responses, or reasoning.
```

### 3. Submit

- **With repo access**: commit and push directly
- **Without repo access**: open a merge request on [GitLab](https://gitlab.syncad.com/hive/hive.support)

## Contribution Types

| Type | When to use |
|------|------------|
| `correction` | A fact in the KB is wrong |
| `addition` | Something is missing that should be there |
| `question` | Unsure about something, want it investigated |
| `inconsistency` | KB says X but the code does Y |
| `cascade` | A conceptual error that likely appears in many places (triggers KB-wide sweep) |

**When to use `cascade`**: Most corrections are local — one wrong number, one missing field. But sometimes the error is conceptual: a term used incorrectly throughout the KB, or a misunderstanding that propagates across multiple documents. Use `cascade` when you suspect the same error appears in more than one place, directly or indirectly.

## Tips

- **Be specific.** "RC section seems wrong" is hard to act on. "rc.md says mana regenerates over 5 days but `rc_utility.cpp:89` uses a different constant" is actionable.
- **Cite source.** If you can point to a file and line number in [hive/hive](https://gitlab.syncad.com/hive/hive), do it.
- **Don't worry about formatting.** Close enough is fine — the pipeline will interpret it.
- **Don't edit reference/ or research/.** Those are pipeline output. Your contribution in `contrib/` is the correct input channel.

## For Agents

The `hive-researcher` and `hive-reviewer` agents are configured to write contrib files automatically when they discover gaps or inconsistencies. If you're building a custom agent that uses this KB, follow the same `contrib/` format — it will be processed identically.
