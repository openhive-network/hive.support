# Rules: haf (indexing framework)
Anchor: HAF 1.28.6 (222c848355efbdf0e4970c5f384b6da7cbfb582e). Source paths are HAF-repo-relative (the KB cites most of them relative to src/hive_fork_manager/); "confirmed in worktree" marks citations verified in workspace/haf/222c848355/ beyond the KB text.
Each rule is derived from the cited hive.support KB sections (reference/haf/*, research/haf/findings/01-07, contrib/haf/2026-07-23) and is meant to be checked in code review of a HAF app.

## HAF-001: Read chain data only through the context's views

- **Rule**: A HAF app reads blocks, transactions and operations only through its own context's auto-generated views (`<schema>.blocks_view`, `operations_view`, `transactions_view`, ...), never from the raw `hafd.*_reversible` tables and never by joining `hafd.blocks` with `hafd.blocks_reversible` itself.
- **Why**: The view is a `UNION ALL` of the irreversible rows (`num <=` the context's `irreversible_block`) and the reversible rows of the context's own fork (per block, the row with `MAX(fork_id) <= ctx.fork_id` and `num <= current_block_num`); the raw reversible tables hold rows from every fork hived has seen, including abandoned ones, and `hafd.blocks` alone stops at the irreversible head.
- **Evidence**: reference/haf/schema.md (The per-context views (the merge)); research/haf/findings/04-data-model.md (2. The per-context views (the reversible/irreversible merge)); reference/haf/README.md (Important Non-Obvious Facts); source: src/hive_fork_manager/blocks_views_for_contexts.sql:76, :149-156 (forking merge), :163 (non-forking variant); operations_view at :521 and :537-540 (confirmed in worktree)
- **Applies**: HAF 1.28.6
- **Detect**: grep app SQL for `_reversible`, `hafd.blocks_reversible`, `hafd.operations_reversible`, `hafd.transactions_reversible`, `fork_id`, `MAX(fork_id)`; `FROM hafd.blocks` / `FROM hafd.operations` inside block-processing code; any app-side "pick the newest fork" logic.
- **Wrong**: `SELECT * FROM hafd.operations_reversible WHERE fork_id = (SELECT MAX(id) FROM hafd.fork) AND ...` to see head-of-chain operations.
- **Right**: `SELECT * FROM my_app.operations_view WHERE block_num BETWEEN _first_block AND _last_block` (the range returned by `app_next_iteration`), with `fork_id` never appearing in app code.

## HAF-002: App objects live in the app schema, not in hive or hafd

- **Rule**: Create the app's tables, functions, views and types in the app's own schema (the `_schema` given to `hive.app_create_context`), never in `hive` or `hafd`, and never run DDL/DML against HAF's `hafd` tables except through the `hive.app_*` API.
- **Why**: Every HAF update drops and recreates the entire `hive` schema (runtime code and views) while `hafd` (persistent data) is never modified; app roles hold CREATE on both schemas (authorization.sql:60, :64, confirmed in worktree), so a misplaced object is accepted silently and then vanishes at the next update.
- **Evidence**: reference/haf/README.md (Important Non-Obvious Facts); reference/haf/schema.md (Schemas); research/haf/findings/01-architecture-dataflow.md (4. The fork manager (Postgres -> apps)); research/haf/findings/02-fork-manager-schema.md (1. The schemas); source: src/hive_fork_manager/Readme.md (schemas section; :24-29 confirmed in worktree); src/hive_fork_manager/authorization.sql:60-67 (confirmed in worktree)
- **Applies**: HAF 1.28.6
- **Detect**: `CREATE (TABLE|FUNCTION|PROCEDURE|VIEW|TYPE|INDEX) hive\.` or `hafd\.` in app migrations; `ALTER TABLE hafd.`, `INSERT INTO hafd.`, `UPDATE hafd.`, `DELETE FROM hafd.`; unqualified `CREATE` statements under a `search_path` that starts with `hive`.
- **Wrong**: `CREATE FUNCTION hive.my_app_parse_memo(...)` - works until the next `hive_fork_manager` update, then the function is gone and the app fails.
- **Right**: `CREATE FUNCTION my_app.parse_memo(...)`; app tables as `CREATE TABLE my_app.t (...)` followed by `SELECT hive.app_register_table('my_app', 't', 'my_app')`.

## HAF-003: events_queue.block_num means a different thing per event type

- **Rule**: Never interpret `hafd.events_queue.block_num` without the `event` column: it is a block number for `NEW_BLOCK` and `NEW_IRREVERSIBLE`, the head irreversible block after a massive push for `MASSIVE_SYNC`, and a fork id (`hafd.fork.id`) for `BACK_FROM_FORK`.
- **Why**: The queue is HAF's single signal channel `(id, event, block_num)` and reuses the one column per type (comment at `events_queue.sql:1-5`); apps consume it indirectly (the cursor is `hafd.contexts.events_id`, advanced by `app_next_block`), so any direct read, typically monitoring, must switch on `event`.
- **Evidence**: reference/haf/schema.md (Events & forks); research/haf/findings/02-fork-manager-schema.md (4. The events queue and forks; 7. Notable findings); reference/haf/README.md (Important Non-Obvious Facts); source: src/hive_fork_manager/events_queue.sql:1-13; src/hive_fork_manager/forks.sql:1; src/hive_fork_manager/context_rewind/data_schema.sql:7
- **Applies**: HAF 1.28.6
- **Detect**: `FROM hafd.events_queue` without `WHERE event = ...` or a `CASE event`; `MAX(block_num)`, `ORDER BY block_num` or `ORDER BY id DESC LIMIT 1` over the queue used as "head block"; joins of `events_queue.block_num` to `hafd.blocks.num` for all rows.
- **Wrong**: `SELECT block_num FROM hafd.events_queue ORDER BY id DESC LIMIT 1` as the current head: after a fork switch the newest row is `BACK_FROM_FORK` and the value is a small fork id.
- **Right**: derive lag from `hafd.contexts.current_block_num` and `hive.app_get_irreversible_block`; if the queue must be read, `SELECT event, CASE WHEN event = 'BACK_FROM_FORK' THEN NULL ELSE block_num END AS block_num, ...`.

## HAF-004: An operation id is |32b block_num|32b seq|, not a counter

- **Rule**: Treat `hafd.operations.id` (also the `id` in `operations_view`) as an encoded key: the block number is its high 32 bits and an in-block sequence its low 32 bits. Derive the block with `hafd.operation_id_to_block_num(id)` or use the view's `block_num` column; never assume ids are dense, never count operations from id differences, and never read an operation type out of the id.
- **Why**: One bigint both sorts and locates an operation, so ids jump by 2^32 at every block boundary and `hafd.operations` carries no `block_num` column of its own (the views compute it from the id). An older HAF encoding kept the op type in the low 8 bits; code doing `id & 255` dates from then and is wrong now (migration comment and backfill at custom_json_type_schema_update.sql:138-150, confirmed in worktree).
- **Evidence**: reference/haf/schema.md (Core tables (irreversible / reversible pairs)); research/haf/findings/04-data-model.md (1. Core tables (columns); 6. Notable findings); reference/haf/README.md (Important Non-Obvious Facts); source: src/hive_fork_manager/irreversible_blocks.sql:100-109 (encoding comment at :101); src/hive_fork_manager/types/operation/operation_id.sql:3, :8, :14 and src/hive_fork_manager/blocks_views_for_contexts.sql:540 (confirmed in worktree)
- **Applies**: HAF 1.28.6
- **Detect**: `id + 1`, `id - 1`, `max(id) - min(id)`, `id & 255`, `id >> 8`, `generate_series` over operation ids, "next page = last id + 1" pagination, hand-rolled `(block_num::bigint << 32) | pos` instead of `hafd.operation_id(block_num, pos)`, `COUNT` replaced by id arithmetic.
- **Wrong**: `SELECT max(id) - min(id) + 1 AS ops_in_block FROM my_app.operations_view WHERE block_num = 50000000`
- **Right**: `SELECT count(*) FROM my_app.operations_view WHERE block_num = 50000000`; for a stored op id use `hafd.operation_id_to_block_num(op_id)`; build ids only with `hafd.operation_id(block_num, pos)`.

## HAF-005: Keep the heartbeat; a silent app gets auto-detached

- **Rule**: The app's loop must keep calling `hive.app_next_block` / `hive.app_next_iteration` (both stamp `hafd.contexts.last_active_at`); work that keeps the loop silent for hours must run with the context deliberately detached (`hive.app_context_detach` ... `hive.app_context_attach`) or must commit and call `hive.app_update_last_active_at(ctx)` periodically, and startup code must handle a context that HAF detached in the meantime.
- **Why**: `last_active_at` is HAF's dead-app detector: a context that stops being stamped is auto-detached so its reversible data and rewind triggers stop pinning the database, and a detached context is paused until re-attached. The detector is `hive.proc_perform_dead_app_contexts_auto_detach(_app_timeout DEFAULT '4 hours')`, scheduled every 30 minutes by pg_cron in the HAF Docker image (hived_api.sql:727, :757; docker/cron_jobs.sql:2; confirmed in worktree).
- **Evidence**: reference/haf/apps.md (Key behaviors); research/haf/findings/03-app-development.md (3. The consume loop; 5. Context lifecycle; 7. Notable findings); research/haf/findings/02-fork-manager-schema.md (2. The context registry; 7. Notable findings); source: src/hive_fork_manager/app_api.sql:198-224 (stamp at :210-212), :240, :331; src/hive_fork_manager/context_rewind/data_schema.sql:9-27; confirmed in worktree: src/hive_fork_manager/hived_api.sql:727, :737, :757; docker/cron_jobs.sql:2; src/hive_fork_manager/app_api.sql:590 (`app_update_last_active_at`); src/hive_fork_manager/application_loop/loop.sql:118-135, :236, :271-278 (`app_next_iteration` stamps and manages attachment)
- **Applies**: HAF 1.28.6
- **Detect**: a loop that calls `app_next_*` once and then runs an unbounded job; "pause" or "maintenance" modes implemented as `sleep` with committed state; backfills or index rebuilds run under the app role for hours with neither `app_update_last_active_at` nor an explicit detach; startup paths that never check `hafd.contexts_attachment.is_attached` or call `hive.app_context_attach` (plain `app_next_block` does not re-attach); no alert on a detached context.
- **Wrong**: a worker that dies Friday night and is restarted Monday with a plain `hive.app_next_block` loop - the context was auto-detached over the weekend and stays paused.
- **Right**: tight loop `CALL hive.app_next_iteration(ctx, range); process the range; COMMIT; repeat` (it manages attachment itself); explicit `hive.app_context_detach` / bulk load / `hive.app_context_attach` for long offline work; an `is_attached` check at startup.

## HAF-006: Choose forking vs non-forking per app, and register what you write

- **Rule**: Decide the context's forking mode explicitly: keep `_is_forking => TRUE` (the default) only when the app must see reversible head blocks and wants automatic rewind of its registered tables; otherwise create it non-forking (`_is_forking => FALSE`, or `hive.app_context_set_non_forking`). Change the mode only through the API, never by `UPDATE hafd.contexts`.
- **Why**: Registered tables of a forking context get the rewind machinery (a shadow undo table in `hafd`, statement-level `AFTER INSERT/UPDATE/DELETE` + `BEFORE TRUNCATE` capture triggers, revert functions), so every app write also writes undo rows and a `BACK_FROM_FORK` event replays them in reverse; a non-forking context is never rewound and both its views and `app_next_block` serve only irreversible blocks (lite mode forces non-forking); its capture triggers are skipped when the context is (re)attached, which is how `hive.app_context_set_non_forking` sheds them (caveat, confirmed in worktree: `hive.register_table` still installs the triggers on any attached context regardless of `is_forking`, so a non-forking context that registers tables while attached carries them until its first detach/attach cycle). `UPDATE (is_forking)` on `hafd.contexts` is revoked from app roles (authorization.sql:76, confirmed in worktree).
- **Evidence**: reference/haf/apps.md (Key behaviors); reference/haf/forks.md (The undo log (set up at app_register_table); Why it matters); research/haf/findings/03-app-development.md (2. Creating a context; 3. The consume loop); research/haf/findings/05-forks-reversibility.md (2. Registration: shadow table + triggers + revert functions; 5. Forking vs non-forking); research/haf/findings/04-data-model.md (2. The per-context views); source: src/hive_fork_manager/app_api.sql:22-55 (lite forcing at :34-37), :198-224 (routing at :218-223), :367, :419, :475; src/hive_fork_manager/context_rewind/register_table.sql:118-122; src/hive_fork_manager/context_rewind/triggers.sql:23, :34, :45, :56; src/hive_fork_manager/blocks_views_for_contexts.sql:163; confirmed in worktree: src/hive_fork_manager/context_rewind/detach_table.sql:98-101, src/hive_fork_manager/context_rewind/register_table.sql:430-432, src/hive_fork_manager/context_rewind/triggers.sql:1-22, src/hive_fork_manager/app_api.sql:367-404, src/hive_fork_manager/app_api_impl.sql:482-495, src/hive_fork_manager/authorization.sql:76
- **Applies**: HAF 1.28.6
- **Detect**: `app_create_context` without an explicit `_is_forking` in apps that only need irreversible data; non-forking apps whose code expects `*_view` to contain the last (reversible) blocks or that implement their own fork handling; `UPDATE hafd.contexts SET is_forking`; forking apps writing to tables that were never registered (`hive.app_register_table`, or `CREATE TABLE ... INHERITS (<ctx>)`, confirmed in worktree), which are not rewound.
- **Wrong**: `SELECT hive.app_create_context('daily_stats', 'daily_stats')` for an aggregates app: it pays shadow-table and trigger overhead on every write for reversible data it never needed.
- **Right**: `SELECT hive.app_create_context('daily_stats', _schema => 'daily_stats', _is_forking => FALSE, _stages => ARRAY[hive.stage('MASSIVE', 2, 100), hafd.live_stage()])`; a head-of-chain app keeps forking and registers every table it writes.
