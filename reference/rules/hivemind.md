# Rules: hivemind (social API layer)
Anchor: hivemind 1.28.6 (cab9e328bfd5bd9da2d228d68db75b07b7ae8f93), the HAF app behind bridge / condenser_api / follow_api / tags_api / database_api; protocol cross-references use the hive-core KB at 1.28.7.
These rules are derived from the cited KB sections (reference/hivemind/ and research/hivemind/findings/); every source line is copied from the KB or confirmed in the pinned worktree workspace/hivemind/cab9e328bf/.

## HM-001: Positional JSON-RPC params bind by the endpoint's expected-args key order

- **Rule**: When `params` is a positional array, hivemind assigns the values to parameter names in the key order of that endpoint's `validate_json_arguments(_params, '{...}')` literal and rejects extra positionals; there is no other positional signature. Prefer a named-params object; if you must go positional, copy the literal's order exactly.
- **Why**: `_expected_args` is typed JSON (not JSONB) precisely because JSON preserves key order; the validator loops `json_each_text(_expected_args)` and binds `_given_args->_idx` to each key in turn, so the literal's key order IS the wire contract (a 1-element array holding an object is unwrapped instead of mapped).
- **Evidence**: reference/hivemind/serving.md (The validator); reference/hivemind/README.md (Important Non-Obvious Facts > API behavior); research/hivemind/findings/05-bridge-api.md (Key Discovery 1); source: hive/db/sql_scripts/postgrest/utilities/validate_json_arguments.sql:2-110 (ordering comment 2, mapping loop 69-75); hive/db/sql_scripts/postgrest/bridge_api/bridge_api_get_ranked_posts.sql:15-86 (literal at line 17: sort, start_author, start_permlink, limit, tag, observer, muted_reasons_filter); hive/db/sql_scripts/postgrest/bridge_api/bridge_api_get_post.sql:15-74 (literal at line 15: author, permlink, observer)
- **Applies**: hivemind 1.28.6
- **Detect**: `"params": [...]` arrays or legacy `call` envelopes (`["bridge", "get_ranked_posts", [...]]`) sent to any hivemind method; client wrappers that build positional arrays from their own argument order (for example `(sort, limit, tag)`); compare each against the endpoint's expected-args literal.
- **Wrong**: `{"method": "bridge.get_ranked_posts", "params": ["trending", 20, "hive-123"]}` meant as (sort, limit, tag): positions 2 and 3 are actually `start_author` and `start_permlink`.
- **Right**: `{"method": "bridge.get_ranked_posts", "params": {"sort": "trending", "tag": "hive-123", "limit": 20}}` (named object), or a positional array strictly in the literal's order.

## HM-002: Vote lists are capped at 1000 per response

- **Rule**: `active_votes` on every bridge/condenser/tags post object and `database_api.find_votes` return at most 1000 votes (hardcoded), and `database_api.list_votes` only accepts `limit` in [1, 1000]. Never derive a vote count or a "has X voted" answer from a returned vote array; to enumerate beyond 1000, page `database_api.list_votes` (order `by_comment_voter`, start `[author, permlink, last_voter]`).
- **Why**: one engine, `hivemind_postgrest_utilities.list_votes(... _limit ...)`, serves all four presentations; both post-object builders pass the literal 1000 ("in python code it was hardcoded"), `find_votes` passes 1000, and `list_votes` validates `valid_number(_limit, 1000, 1, 1000)`. Only the interactive `list_votes` has a cursor (`voter_id >= start voter`, ordered by voter id).
- **Evidence**: reference/hivemind/api.md (Common rules; database_api (3)); reference/hivemind/README.md (Key Numbers); research/hivemind/findings/06-legacy-apis.md (Key Discovery 3); research/hivemind/findings/05-bridge-api.md (Key Discovery 4); source: hive/db/sql_scripts/postgrest/utilities/list_votes.sql:1-106; hive/db/sql_scripts/postgrest/utilities/create_bridge_post_object.sql:69-70; hive/db/sql_scripts/postgrest/database_api/database_api_find_votes.sql:32; hive/db/sql_scripts/postgrest/database_api/database_api_list_votes.sql:42,64-66
- **Applies**: hivemind 1.28.6
- **Detect**: `active_votes.length` / `votes.length` used as a count or as pagination end-detection; `active_votes.some(v => v.voter === me)` on popular posts; `find_votes` used to list all voters; `list_votes` called with `limit` > 1000 (raises a validation error).
- **Wrong**: `const voteCount = post.active_votes.length; const iVoted = post.active_votes.some(v => v.voter === me);`
- **Right**: counts from the post's counters (bridge `stats.total_votes`, condenser `net_votes` in `get_content`); membership or full enumeration via `database_api.list_votes` with order `by_comment_voter`, using the last voter of the previous page as the start cursor (inclusive, so drop the repeated first row).

## HM-003: hive_posts.is_declined is never written; infer declined payout from max_accepted_payout

- **Rule**: Do not read `hivemind_app.hive_posts.is_declined`: nothing writes it, so it is FALSE for every post that ever existed. A post declined its payout iff `max_accepted_payout = '0.000 HBD'` (exposed on bridge and condenser post objects and stored on the table). Hivemind's payout/trending sorts do not exclude such posts, so filter client-side if you need to.
- **Why**: the column exists only in the DDL (definition-only since the 2018 draft schema, verified across 0.25.4 .. 1.28.6); the comment_options handler writes `max_accepted_payout`, `percent_hbd`, `allow_votes`, `allow_curation_rewards` and `beneficiaries` and never derives a decline flag. Declined posts still accumulate `pending_payout` (zeroed at cashout), so they rank in payout-sorted lists and `payout_stats_view`.
- **Evidence**: reference/hivemind/README.md (L1 consistency); research/hivemind/findings/08-l1-consistency.md (Key Discovery 11); reference/hivemind/operations.md (The op filter (staging), op 19 comment_options); source: hive/db/sql_scripts/schema/create_tables.sql:44; hive/db/sql_scripts/massive_sync.sql:1212-1248
- **Applies**: hivemind 1.28.6 (column definition-only from 0.25.4 through 1.28.6 per the KB)
- **Detect**: SQL containing `is_declined` (`WHERE NOT hp.is_declined`, `SELECT ... is_declined`) in HAF apps, analytics or admin tooling; UI "Declined payout" logic keyed on anything but `max_accepted_payout`; assumptions that `payout`-sorted lists already exclude declined posts.
- **Wrong**: `SELECT id FROM hivemind_app.hive_posts WHERE is_declined` (always empty) or `WHERE NOT is_declined` (excludes nothing).
- **Right**: `WHERE max_accepted_payout <> '0.000 HBD'` on the table; `post.max_accepted_payout === '0.000 HBD'` on API objects to render the badge or drop the post from a payout list.

## HM-004: Filter counter_deleted = 0 (or use the live_* views) when reading hivemind tables

- **Rule**: `hive_posts` rows are unique on `(author_id, permlink_id, counter_deleted)`: a deleted post keeps its row with a bumped counter, and its permlink can be reused by a NEW row with a new id. Every direct query must restrict to `counter_deleted = 0` (what `live_posts_comments_view` / `live_posts_view` / `live_comments_view` encode) and skip the sentinel `id = 0`.
- **Why**: deletes and delete-create cycles never remove rows; `find_comment_id` and almost every `hive_posts` partial index are predicated on `counter_deleted = 0`, so a lookup by `(author, permlink)` alone can return several rows including dead revisions, and ids are not stable across a delete + re-create (votes do not carry over to the new row).
- **Evidence**: reference/hivemind/schema.md (Core tables (21); Views); reference/hivemind/README.md (Data model / indexer); research/hivemind/findings/02-schema-data-model.md (Key Discovery 3); research/hivemind/findings/04-operation-semantics.md (Posts (create/edit/delete)); source: hive/db/sql_scripts/schema/create_tables.sql:70; hive/db/sql_scripts/hive_posts_view.sql:1-5; hive/db/sql_scripts/postgrest/utilities/find_comment_id.sql:20 (confirmed in worktree); hive/db/schema.py:47-79 (seed sentinel rows)
- **Applies**: hivemind 1.28.6
- **Detect**: SQL on `hivemind_app.hive_posts` (or `hive_post_data` joined by id, `hive_votes.post_id`) with no `counter_deleted = 0` predicate and no `live_*` view; joins keyed only on `author_id, permlink_id`; cached post ids assumed immutable across deletes; `hp.id = 0` not excluded from aggregates.
- **Wrong**: `SELECT hp.id FROM hivemind_app.hive_posts hp JOIN hivemind_app.hive_accounts a ON a.id = hp.author_id JOIN hivemind_app.hive_permlink_data p ON p.id = hp.permlink_id WHERE a.name = $1 AND p.permlink = $2` (may return the live post plus its deleted predecessors).
- **Right**: the same query against `hivemind_app.live_posts_comments_view` (or add `AND hp.counter_deleted = 0 AND hp.id <> 0`); re-resolve ids after a delete/re-create instead of caching them.

## HM-005: Reputation comes in two scales: raw in condenser/follow/tags, rep_log10 in bridge

- **Rule**: `condenser_api` (and the `tags_api` / `follow_api` delegations) return the RAW reputation bigint (`author_reputation` on post objects, `get_account_reputations`), while `bridge` post objects and `bridge.get_profile(s)` return the display value `rep_log10 = (log10(rep) - 9) * 9 + 25` (0 -> 25, sign-preserving, 2 decimals). Convert raw values once, client-side; never convert bridge values again; and do not reuse either for notification `score`, which is `(GREATEST(log10|rep| - 9, 0) * sign * 7.5 + 25)`.
- **Why**: `create_condenser_post_object` emits `_row.author_rep` untouched; `create_bridge_post_object` and `get_profiles` pass it through `hivemind_postgrest_utilities.rep_log10()`; the indexer's `reputation_score()` uses `*7.5` so notification scores top out at 100.
- **Evidence**: reference/hivemind/api.md (Response objects (bridge vs condenser)); reference/hivemind/serving.md (Utility belt); reference/hivemind/README.md (API behavior); research/hivemind/findings/06-legacy-apis.md (Key Discovery 2); research/hivemind/findings/07-serving-internals.md (The utility belt); research/hivemind/findings/04-operation-semantics.md (Key Discovery 6); source: hive/db/sql_scripts/postgrest/utilities/rep_log10.sql:1-35; hive/db/sql_scripts/postgrest/utilities/create_condenser_post_object.sql:35; hive/db/sql_scripts/postgrest/utilities/create_bridge_post_object.sql:2-148 (rep_log10 applied at lines 14 and 68, confirmed in worktree); hive/db/sql_scripts/postgrest/utilities/get_profiles.sql:29-67; hive/db/sql_scripts/massive_sync.sql:2402-2409
- **Applies**: hivemind 1.28.6
- **Detect**: one `formatReputation()` helper applied to results of both namespaces; `condenser_api.get_content` / `get_account_reputations` values rendered without conversion (15-digit numbers in the UI); bridge `author_reputation` or profile `reputation` fed into a log10 formula; equality checks between condenser and bridge reputation values.
- **Wrong**: `repLog10(bridgePost.author_reputation)` (double conversion) or `<span>{condenserPost.author_reputation}</span>` (raw bigint on screen).
- **Right**: `repLog10(condenserPost.author_reputation)` only for condenser/follow/tags data; `bridgePost.author_reputation` as-is; notification `score` displayed on its own 0-100 scale.

## HM-006: Social custom_json: four ids, exactly one posting auth, actor = the signer

- **Rule**: Hivemind interprets a custom_json only when `id` is `follow`, `reblog`, `community` or `notify` AND the op has exactly one `required_posting_auths` entry and an empty `required_auths`; the acting account is that posting auth (`follower` / `account` in the payload must equal it). An active-key-signed follow/reblog/community op, or any other id, is valid on L1 (RC charged, included in a block) but never changes hivemind state.
- **Why**: `load_ops_staging` keeps op 18 only for those 4 ids via HAF's `custom_json_type_id`, and every consumer (follows, reblogs, `setLastRead`, community ops) skips rows unless `jsonb_array_length(required_auths) = 0` and `jsonb_array_length(required_posting_auths) = 1`; L1 itself only requires 1-40 auths of either kind, so the chain cannot catch the mistake for you.
- **Evidence**: reference/hivemind/operations.md (The op filter (staging); Follow custom_json; Reblog custom_json); reference/hivemind/README.md (API behavior; L1 consistency); research/hivemind/findings/08-l1-consistency.md (Key Discovery 6, 7); research/hivemind/findings/03-sync-internals.md (Key Discovery 1); reference/operations.md (custom_json_operation (ID: 18), hive-core KB); source: hive/db/sql_scripts/massive_sync.sql:168-208; hive/db/sql_scripts/hafapp_api.sql:108-115,165-168; hive/db/sql_scripts/massive_sync.sql:533-539,571-576,700-707,2151-2157; hive/indexer/hive_db/haf_functions.py:9,39-48
- **Applies**: hivemind 1.28.6
- **Detect**: `custom_json` ops built with `required_auths: [account]` and empty `required_posting_auths` for follow/reblog/community/notify payloads; a signer or wallet defaulting to the active key; two posting auths; payload `follower`/`account` differing from the signer; code expecting hivemind to index an app-specific id (e.g. `my-app`) into follows or notifications.
- **Wrong**: `{"id": "follow", "required_auths": ["alice"], "required_posting_auths": [], "json": "[\"follow\",{\"follower\":\"alice\",\"following\":\"bob\",\"what\":[\"blog\"]}]"}` (accepted by hived, ignored by hivemind).
- **Right**: `{"id": "follow", "required_auths": [], "required_posting_auths": ["alice"], "json": "..."}` signed with alice's posting key and `follower` = `alice`.

## HM-007: Errors masquerade as hived assert_exception; unknown method is -32602, unknown API is -32601

- **Rule**: Treat hivemind JSON-RPC errors like hived errors: prominent failures (unknown method, invalid account/permlink, deleted post, ...) carry a fabricated `data` payload `{code: 10, name: "assert_exception", stack: [...], assert_hash}`; an unknown method in a known namespace returns JSON-RPC code -32602 with message `Assert Exception:unknown method: ...` (not -32601), while an unknown namespace returns -32601 `Api not found <api>` with no data. Do not use -32601 or the `data` shape to detect a missing method or to tell hivemind from hived.
- **Why**: endpoint functions RAISE a JSON string that `home()` re-parses into the error object; `build_hived_error_data` fabricates a hived-style structure labeled "WAX-compatible" so wax/beem error handling works unchanged; `raise_method_not_found_exception` hardcodes -32602 as a faithful port of the old Python server.
- **Evidence**: reference/hivemind/serving.md (Error contract); reference/hivemind/README.md (API behavior); research/hivemind/findings/07-serving-internals.md (Key Discovery 1); research/hivemind/findings/01-architecture-deployment.md (10.3 The JSON-RPC dispatcher); source: hive/db/sql_scripts/postgrest/utilities/exceptions.sql:3-36,39-62,90-112; hive/db/sql_scripts/postgrest/home.sql:63-76; hive/db/sql_scripts/postgrest/utilities/exceptions.sql:114-125 and hive/db/sql_scripts/postgrest/utilities/dispatch.sql:11-31 (api-not-found path returns -32601, confirmed in worktree)
- **Applies**: hivemind 1.28.6
- **Detect**: `error.code === -32601` used for method feature-detection or fallback; `error.data.name === 'assert_exception'` or `data.code === 10` routed to a "node rejected my transaction" handler; code keying on `assert_hash` or the fake stack frame.
- **Wrong**: `if (err.code === -32601) { fallbackToCondenser(); }` (never fires for an unknown bridge method) or `if (err.data?.name === 'assert_exception') reportHivedError(err)`.
- **Right**: match `err.code === -32602 && /unknown method:/.test(err.message)` for a missing method (and -32601 only for an unknown namespace); if you must attribute origin, the fabricated frame carries `data.stack[0].data.category === 'hivemind'` (exceptions.sql:3-36).
