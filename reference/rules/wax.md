# Rules: wax (client library)
Anchor: wax 2.0.2 (c9c4918a845f59ebd97fff1316d00c91827df623, npm latest; PyPI hiveio-wax 2.0.1 where Python is noted); protocol facts cross-referenced from the hive-core KB (release 1.28.7).
Rules are derived from the cited hive.support KB sections (reference/wax/*.md, research/wax/findings/01..07) and their file:line citations were re-checked in the pinned worktree workspace/wax/c9c4918a84/.

## WAX-001: NaiAsset.amount is a string of smallest units, not a decimal number

- **Rule**: Treat `NaiAsset.amount` as a string holding the integer count of smallest units (1.000 HIVE is `"1000"` at precision 3; VESTS uses precision 6) and build assets with the typed builders: `hiveSatoshis` / `hbdSatoshis` / `vestsSatoshis` (smallest units) or `hiveCoins` / `hbdCoins` / `vestsCoins` (whole coins) instead of hand-assembling `{ amount, precision, nai }`.
- **Why**: `amount` is BigInt-backed so balances survive without floating-point loss; `Number(amount)` or reading `"1000"` as 1000 HIVE silently mis-scales by 10^precision, and a hand-built object with a wrong `nai` or `precision` is rejected by `createAssetWithRequiredSymbol` -> `assertAssetSymbol` with a `WaxError` when a builder or economics helper requires a specific symbol.
- **Evidence**: reference/wax/assets.md (NaiAsset; Building (TypeScript)); research/wax/findings/04-assets-formatters.md (1. The three native assets and the NAI representation; 2. Building assets (TypeScript) - Coercion and validation; 6. Notable findings #1, #5); source: ts/wasm/lib/detailed/api/types/asset.ts:1-5; ts/wasm/lib/detailed/base_api.ts:223-257; ts/wasm/lib/detailed/base_api.ts:126-139
- **Applies**: wax 2.0.2 (TS); Python 2.0.1 exposes the same builders (`wax.hive(n)` via `AssetFactory`, `python/wax/wax/_private/base_api.py:149-157`) and the `python_json_asset` value type, so the units rule holds there too.
- **Detect**: `Number(x.amount)`, `parseFloat(x.amount)`, `+x.amount`, arithmetic directly on `.amount`; object literals `{ amount: ..., precision: 3, nai: "@@000000021" }` typed by hand; `hiveSatoshis(1.5)` / `hive(1.5)` (fractional smallest units) where `hiveCoins(1.5)` was meant; `.toFixed(3)` applied to a raw amount.
- **Wrong**: `amount: { amount: 1.5, precision: 3, nai: "@@000000021" }` inside a `transfer_operation` (a JS number holding whole coins in a smallest-unit field)
- **Right**: `amount: chain.hiveCoins(1.5)` or `amount: chain.hiveSatoshis(1500)`; keep `.amount` a string and use `BigInt(asset.amount)` if arithmetic is unavoidable.

## WAX-002: Render amounts with waxify / formatNumber in TypeScript; Python has no formatter

- **Rule**: In TypeScript, render assets for display through `wax.waxify` (template tag), `wax.formatter.format(obj)` or `wax.formatter.formatNumber(amount, precision?, locales?)` instead of hand-rolled `toFixed` / `Intl.NumberFormat` arithmetic on the raw amount; Python (`hiveio-wax`) has no `waxify` equivalent, so Python code must format from `amount` and `precision` itself.
- **Why**: `formatNumber` is BigInt-based and locale-aware and handles arbitrary precision (amounts can exceed `MAX_SAFE_INTEGER`, and `Intl.NumberFormat` caps precision at 20); `DefaultFormatters` render a `NaiAsset` (matched on its `nai` property) as `"1.000 HIVE"` via `getAsset` + `formatNumber`, and the formatter is a TypeScript-only convenience (`formatters/` exists only in the TS package).
- **Evidence**: reference/wax/assets.md (waxify formatter (TypeScript-only)); research/wax/findings/04-assets-formatters.md (4. The waxify formatter (TypeScript); 5. Python parallel; 6. Notable findings #4); source: ts/wasm/lib/detailed/formatters/waxify.ts:60-85; ts/wasm/lib/detailed/formatters/base.ts:72; ts/wasm/lib/detailed/formatters/base.ts:76; ts/wasm/lib/detailed/formatters/default_formatters.ts:13-30; ts/wasm/lib/detailed/base_api.ts:67-70
- **Applies**: wax 2.0.2 (TS); Python 2.0.1 has assets and conversions but no formatter.
- **Detect**: `(Number(amount) / 1000).toFixed(3)`, `parseInt(amount) / 10 ** precision`, `Intl.NumberFormat(...).format(Number(amount))`, hardcoded `/ 1e6` for VESTS, a third-party money formatter applied to Hive assets in TS; Python code that expects `waxify` / `formatter` on the chain object.
- **Wrong**: `` `${(Number(bal.amount) / 1000).toFixed(3)} HIVE` ``
- **Right**: `` wax.waxify`Balance: ${bal}` `` (renders "1.000 HIVE" through `DefaultFormatters`) or `wax.formatter.format(bal)`; add app-specific rendering with `wax.formatter.extend(CustomFormatter)`.

## WAX-003: Do not call the deprecated Transaction.sign(); use a signer's signTransaction or sigDigest + addSignature

- **Rule**: In TypeScript sign through a signer package (`XxxProvider.for(chainOrBase, backend, pubKeyOrAccount, role?)` then `await provider.signTransaction(tx)`) or manually via `tx.sigDigest` -> sign externally -> `tx.addSignature(sig)`; `Transaction.sign(provider, publicKey)` is marked `@deprecated`. Private keys never enter wax: a provider only returns signatures.
- **Why**: `ASignatureProvider.signTransaction` = `generateSignatures(tx)` then `addSignature` for each signature, and `AEncryptionProvider.signTransaction` runs `performOperationEncryption` (memo encryption) before signing, so the provider path gives encrypt-then-sign plus role-key resolution (`database_api.find_accounts`, which makes `for(..., role)` return a Promise); all five signer packages (`@hiveio/wax-signers-{beekeeper,keychain,metamask,peakvault,external}`) plug into this flow, and the digest (not the transaction bytes) is what gets signed.
- **Evidence**: reference/wax/signing.md (Provider abstraction; Signer packages (npm, pluggable)); reference/wax/transactions.md (Gotchas); research/wax/findings/05-signing-signers.md (1. The provider abstraction (3 interfaces + 2 base classes); 2. Signer packages (pluggable backends)); research/wax/findings/03-transaction-lifecycle.md (7. Signing); source: ts/wasm/lib/detailed/transaction.ts:386-397; ts/wasm/lib/detailed/transaction.ts:399-405; ts/wasm/lib/detailed/extensions/signatures/extension_helpers.ts:7-39; ts/packages/signers-beekeeper/src/index.ts:36-48; ts/packages/signers-beekeeper/src/index.ts:85-89
- **Applies**: wax 2.0.2 (TS). Python 2.0.1 diverges: `await tx.sign(wallet, public_key)` with a beekeepy unlocked wallet is the supported path (`python/wax/wax/_private/transaction.py:113-115`); the browser signers (keychain / metamask / peakvault) are TS-only.
- **Detect**: `tx.sign(` / `.sign(provider,` in TS code; `wallet.signDigest(` fed anything other than `tx.sigDigest`; a WIF private key handed to wax to produce a signature; `Provider.for(..., role)` used without `await` (with a role it returns a Promise, so `.signTransaction` is undefined on the bare return value).
- **Wrong**: `tx.sign(provider, publicKey)` (deprecated) or `wallet.signDigest(pubKey, tx.toBinaryForm())` (signs bytes, not the digest)
- **Right**: `const provider = await BeekeeperProvider.for(chain, wallet, "alice", "active"); await provider.signTransaction(tx); await chain.broadcast(tx);`

## WAX-004: sigDigest binds the chain id; set chainId for any non-mainnet chain

- **Rule**: Pass `chainId` in the `createHiveChain` / `createWaxFoundation` options (Python: `chain_id` in `WaxOptions` / `WaxChainOptions`) whenever the target chain is not Hive mainnet; the default is the literal mainnet id `beeab0de00000000000000000000000000000000000000000000000000000000` and `tx.sigDigest` is `cpp_tx_sig_digest(handle, chainId, true)`, so a signature made under the wrong id is invalid on the target chain.
- **Why**: the chain id is folded into the signing digest as the cross-chain replay guard (identical operations sign to different digests on mainnet / testnet / mirrornet); the same `chainId` also selects the expiration reference (mainnet: local realtime; any other id: the supplied head block time), so a wrong id silently changes two behaviours at once.
- **Evidence**: reference/wax/README.md (Important Non-Obvious Facts: sigDigest binds the chain id); reference/wax/api.md (Options (defaults)); research/wax/findings/03-transaction-lifecycle.md (7. Signing - The digest; 11. Notable findings #4); research/wax/findings/01-architecture.md (4. API classes and defaults); source: ts/wasm/lib/detailed/transaction.ts:258-268; ts/wasm/lib/detailed/transaction.ts:62-70; ts/wasm/lib/detailed/base.ts:9-11; core/foundation.hpp:279; hive-core libraries/protocol/include/hive/protocol/config.hpp:142
- **Applies**: wax 2.0.2 (TS); Python 2.0.1 (`tx_sig_digest(h, chain_id, use_hf26_serialization=True)`, `python/wax/wax/_private/transaction.py:87-89`; `create_hive_chain(WaxChainOptions(...))`, `python/wax/wax/wax_factory.py:20-29`).
- **Detect**: `createHiveChain({ apiEndpoint: "<testnet or mirrornet node>" })` with no `chainId`; app code that computes the mainnet id as `sha256("beeab0de...")` (it is the literal value, not a hash); a test suite that signs with mainnet config and replays against a local test chain; `legacy_sigDigest` used as a "testnet mode".
- **Wrong**: `const chain = await createHiveChain({ apiEndpoint: "https://testnet.example" });` then sign and broadcast
- **Right**: `const chain = await createHiveChain({ apiEndpoint: "https://testnet.example", chainId: "<the test chain's id>" });`

## WAX-005: Expiration is locked at the first flush (serialize / sign / id), not at construction

- **Rule**: The default expiration `"+1m"` is resolved by `flushTransaction()` the first time anything flushes the transaction (`sigDigest`, `id`, `toApi` / `toString`, `toApiJson`, `toBinaryForm`, `toLegacyApi`, the `transaction` getter, signing) and never again; do not flush a transaction for a preview or log and then wait for user action before signing, or pass an explicit `expirationTime` to `chain.createTransaction(expirationTime?)` sized to the expected wait (protocol maximum `HIVE_MAX_TIME_UNTIL_EXPIRATION` = 3,600 s).
- **Why**: `flushTransaction()` calls `applyExpiration()` only while `target.expiration` is empty, so the relative window is turned into an absolute time exactly once; on mainnet the reference is local realtime at that first flush (to avoid API-node clock skew), on non-mainnet chain ids it is the head block time captured at `createTransaction` (cached up to 3 s). Holding an unflushed transaction costs nothing; holding a flushed one burns the window.
- **Evidence**: reference/wax/transactions.md (Stages: Expiration; Gotchas); research/wax/findings/03-transaction-lifecycle.md (4. Expiration (lazy, locked once); 2. Creating a transaction - Online; 11. Notable findings #1, #2, #6); reference/constants.md (HIVE_MAX_TIME_UNTIL_EXPIRATION); source: ts/wasm/lib/detailed/transaction.ts:63; ts/wasm/lib/detailed/transaction.ts:66-70; ts/wasm/lib/detailed/transaction.ts:168-172; ts/wasm/lib/detailed/transaction.ts:339-344; ts/wasm/lib/detailed/chain_api.ts:185-188; ts/wasm/lib/detailed/util/expiration_parser.ts:21-50 (worktree-confirmed: relative form is "+N" seconds, "+Nm" minutes, "+Nh" hours; a string without "+" is parsed as an absolute date)
- **Applies**: wax 2.0.2 (TS); Python 2.0.1 mirrors the lazy, once-only `_apply_expiration` (`python/wax/wax/_private/transaction.py:177-184`).
- **Detect**: `tx.id`, `tx.toApi()`, `tx.sigDigest`, `tx.transaction` or `JSON.stringify(tx...)` evaluated before a confirmation dialog, queue hand-off or retry loop that signs later; a built transaction cached across requests; comments assuming the clock starts at `createTransaction()`; no `expirationTime` where a human-in-the-loop delay is expected.
- **Wrong**: `const preview = tx.toApi(); await askUserToConfirm(preview); await provider.signTransaction(tx);` (the one-minute window started at the preview)
- **Right**: build and flush only when ready to sign and broadcast (or rebuild after confirmation), or create with an explicit window, e.g. `await chain.createTransaction("+10m")`, keeping it at or below 3,600 s.

## WAX-006: tx.validate() is offline-only; chain-state checks come from OnlineTransaction and broadcast

- **Rule**: `tx.validate()` runs `cpp_tx_validate`: structural/protocol validation of the transaction with no network access; it cannot see chain state (account existence, current authorities). For API-backed checks use the `OnlineTransaction` returned by `chain.createTransaction()`: its async `validate(operations)` hooks resolve accounts through the API and `performOnChainVerification()` runs recursive authority verification, which `chain.broadcast(tx)` invokes before `network_broadcast_api.broadcast_transaction` only when the object has that method.
- **Why**: wax splits an offline foundation from the online chain; `OnlineTransaction` wraps the required accounts in an `AccountAuthorityCachingProvider`, exposes it to C++ via `IAccountAuthorityProvider.implement`, and loops `acquireData()` + `cpp_trace_authority_verification` while deeper `account_auths` layers remain, something the offline validator has no data for. An offline `new Transaction(...)` passed to `broadcast` skips that pre-check entirely.
- **Evidence**: reference/wax/transactions.md (Stages: Validate); reference/wax/api.md (Broadcast); research/wax/findings/03-transaction-lifecycle.md (9. Validation and broadcast); research/wax/findings/06-chain-api-client.md (5. Broadcast); research/wax/findings/05-signing-signers.md (3. Required authorities and online verification); source: ts/wasm/lib/detailed/transaction.ts:335; core/foundation.hpp:283; ts/wasm/lib/detailed/online_transaction.ts:36; ts/wasm/lib/detailed/online_transaction.ts:185-210; ts/wasm/lib/detailed/chain_api.ts:110-117
- **Applies**: wax 2.0.2 (TS); Python 2.0.1 has the same split (`Transaction` vs `OnlineTransaction`, `python/wax/wax/_private/online_transaction.py:123`).
- **Detect**: comments or tests asserting that `validate()` catches a missing account or a wrong signing key; `validate()` in a try/catch as the sole pre-broadcast gate; an offline `new Transaction(api, {...})` or `Transaction.fromApi(...)` handed to `chain.broadcast` where an authority pre-check was expected; `addSignature` treated as proof that the signer is authorized (it only runs `validate()` then appends).
- **Wrong**: `tx.validate(); /* "accounts and keys verified" */ await chain.broadcast(tx);` with an offline `Transaction`
- **Right**: `const tx = await chain.createTransaction(); tx.pushOperation(...); await provider.signTransaction(tx); await chain.broadcast(tx);` (an `OnlineTransaction`, so authority verification runs inside `broadcast`); keep `validate()` for offline structural checks only.

## WAX-007: chain.restApi is empty until extendRest(); chain.api is a curated JSON-RPC subset; node errors are typed Wax* exceptions

- **Rule**: Define HAF/REST endpoints with `chain.extendRest<T>(defs)` and call them on the returned instance; `chain.api` predefines only `account_by_key_api`, `database_api`, `network_broadcast_api`, `block_api` and `rc_api`, so any other hived API (e.g. `condenser_api`) needs `chain.extend<T>(defs)`. Handle failures as thrown `Wax*` exceptions (all extend `WaxError`; a `WaxChainApiError` carries the request/response, as the thrown error or as its `cause`), not as HTTP status checks or `response.error` inspection.
- **Why**: `HiveRestApiTypes = {}` and `HiveApiTypes` is a typed registry; `chain.api` / `chain.restApi` are Proxies whose request is derived from the accessed path plus the registry entry, and the JSON-RPC response interceptor unwraps `result`, converts an `error.data` payload through `cpp_transform_api_error_response_into_exception` into a typed exception whose `cause` is a `WaxChainApiError`, and throws `WaxChainApiError("Invalid response ...")` for anything else. `extend` / `extendRest` return a new instance (the original is untouched).
- **Evidence**: reference/wax/api.md (Calling the API (TypeScript); Extending); reference/wax/README.md (Important Non-Obvious Facts: REST API surface is empty by default; hived API errors become typed Wax* exceptions); research/wax/findings/06-chain-api-client.md (3. JSON-RPC envelope and typed API errors; 4. Predefined API surface and extending it; 10. Notable findings #1, #2, #5); source: ts/wasm/lib/detailed/chain_api_data.ts:12-14; ts/wasm/lib/detailed/chain_api_data.ts:16-73; ts/wasm/lib/detailed/chain_api.ts:68-100; ts/wasm/lib/detailed/chain_api.ts:155; ts/wasm/lib/detailed/chain_api.ts:170; core/foundation.hpp:120; ts/wasm/lib/detailed/errors.ts:5-55 (worktree-confirmed class hierarchy)
- **Applies**: wax 2.0.2 (TS). Python 2.0.1 diverges: one `endpoint_url`, no separate REST caller, APIs are class-based collections merged with `chain.extends(ApiCollection)` (`python/wax/wax/_private/chain_api.py:70-85`).
- **Detect**: `chain.restApi.` with no preceding `extendRest<`; `chain.api.condenser_api.` with no `extend<`; the return value of `extend` / `extendRest` discarded; a hand-rolled `fetch` JSON-RPC client next to wax; `catch (e) { if (e.status === 500) ... }` or `if (res.error)` around `chain.api` calls; no `instanceof WaxError` / `WaxChainApiError` anywhere in API error handling.
- **Wrong**: `await chain.restApi.hafbe.block({...})` on a plain `createHiveChain()` result, with `catch (e) { if (e.response?.status === 404) ... }`
- **Right**: `const chain = (await createHiveChain()).extendRest<MyHafApi>(defs); const r = await chain.restApi.myApi.method({...});` with `catch (e) { if (e instanceof WaxError) { /* e.cause may be a WaxChainApiError with request/response */ } }`

## WAX-008: wax does not recover from WASM heap corruption; long-lived processes must rebuild the instance

- **Rule**: In any long-lived process (server, worker, bot) that keeps a `createHiveChain()` / `createWaxFoundation()` object alive, detect WASM runtime failures (`memory access out of bounds`, `unreachable`, a `RuntimeError` mentioning wasm) and discard and rebuild the wax instance yourself; wax's `WasmManager` caches the Emscripten module in `mainModule` and never resets it.
- **Why**: `safeWasmCall` only translates thrown C++ exceptions into typed `Wax*` errors (unrecognized ones become a generic `WaxError`), so a module whose heap is corrupted stays poisoned for the process lifetime; recovery (detect -> drop cached instance -> rebuild on next call) is implemented by consumers such as denser, not by wax. Each `createHiveChain` / `createWaxFoundation` call constructs a fresh `WasmManager` and loads the module anew.
- **Evidence**: reference/wax/README.md (Important Non-Obvious Facts: No WASM heap-corruption recovery in wax core); research/wax/findings/01-architecture.md (4. TypeScript binding - WasmManager: lifecycle and error translation; 8. Notable findings #1); source: ts/wasm/lib/detailed/util/wasm_errors.ts:17; ts/wasm/lib/detailed/util/wasm_errors.ts:75-81; ts/wasm/lib/detailed/util/wasm_errors.ts:85-99; ts/wasm/lib/detailed/base.ts:9-23; ts/wasm/lib/detailed/chain.ts:12-36
- **Applies**: wax 2.0.2 (TS, WASM binding). Python 2.0.1 binds a native Cython `.so`, not WASM, so this rule is TS-specific.
- **Detect**: a module-level `export const chain = await createHiveChain()` singleton in a server with no error-path re-initialization; `catch` blocks that log a `RuntimeError` / `WaxError` and keep using the same `chain`; a retry loop that re-issues the failing call on the same instance; no "re-create wax" code path at all in a process expected to run for days.
- **Wrong**: `export const chain = await createHiveChain();` used for the process lifetime; on `RuntimeError: memory access out of bounds` the handler retries the same call on the same object.
- **Right**: hold the chain behind a getter; on a WASM `RuntimeError` / `unreachable` / out-of-bounds error, log it, clear the cached reference, and let the next call run `createHiveChain()` again (new `WasmManager`, fresh module), as the denser WASM-corruption fix referenced by the KB does.
