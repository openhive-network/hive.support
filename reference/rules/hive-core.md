# Rules: hive-core (protocol layer)
Anchor: hive-core release 1.28.7, commit 1584099c3054a97f02abfb4788b23f02eea98728 (mainnet at HF28, activated 2025-11-19; hardfork activation is time + witness vote, never the software version).
Every rule below is derived from the cited hive.support KB sections (reference/, research/hive-core/findings/, contrib/hive-core/); source citations are copied from the KB text or were confirmed line-by-line in the pinned worktree where marked.

## HC-001: Sign with the exact authority role; HF28 removed role upgrade and allowed mixing

- **Rule**: Sign every operation with the key of the role it requires: posting for vote, comment, delete_comment, comment_options, claim_reward_balance and custom_json posting auths; active for transfers, power-up/down, orders, witness and DHF ops; owner only for account_update/account_update2 with the owner field set, change_recovery_account and decline_voting_rights. Since HF28 an owner key no longer satisfies an active or posting requirement and an active key no longer satisfies a posting requirement; in exchange, posting-level and active/owner-level operations may now share one transaction and unused extra signatures are tolerated.
- **Why**: `verify_authority_impl` is driven by the HF28 flag `allow_strict_and_mixed_authorities`: before HF28 it rejected posting mixed with active/owner/witness (posting isolation) but accepted role upgrade (posting satisfied by active or owner, active by owner) and rejected unused signatures (`tx_irrelevant_sig`); after HF28 both the isolation rule and the upgrade paths are gone (strict per-role `check_authority`) and `allow_redundant_signatures` is on.
- **Evidence**: research/hive-core/findings/01-protocol-foundation.md (Discovery 14 "Authority Verification: Posting Isolation, Role Upgrade, and the HF28 Strict and Mixed Switch"; "Verification Algorithm"); research/hive-core/findings/02-operations-catalog.md (Posting authority cannot be mixed with active/owner in one transaction before HF28); research/hive-core/findings/09-hardfork-history.md (HF28 sub-features `ALLOW_STRICT_AND_MIXED_AUTHORITIES`, `ALLOW_REDUNDANT_SIGNATURES`); reference/operations.md (Index Table, Authority column); source: libraries/protocol/transaction_util.cpp:59-74, libraries/protocol/transaction_util.cpp:101-104, libraries/protocol/transaction_util.cpp:146-158, libraries/chain/database.cpp:2612-2613
- **Applies**: HF28+ for strict roles and mixing (pre-HF28: posting isolation plus role upgrade); current: HF28, hived 1.28.7
- **Detect**: key-selection fallbacks such as `key = ownerKey || activeKey || postingKey`; comments like "sign with active, it covers posting"; wallets that always use the highest-privilege key available; builders that refuse to batch a vote with a transfer "because Hive forbids it" (true only before HF28); error strings `missing_posting`, `missing_active`, `mixed_with_posting`, `unused_signature`.
- **Wrong**: `tx.sign(activeKey)` for a transaction that contains only a `vote_operation` (accepted before HF28 through role upgrade, rejected now with `missing_posting`).
- **Right**: Resolve the required role per operation (`database_api.get_required_signatures` / `verify_authority` for checks) and sign with exactly that role's key; keep the owner key offline except for owner-level operations.

## HC-002: A vote on a paid-out comment is a silent consensus no-op that still costs RC

- **Rule**: Treat a `vote_operation` on a comment past its cashout as a transaction that succeeds but changes nothing: no voting or downvote mana is consumed, no `comment_vote_object` is created or edited, no `effective_comment_vote_operation` is emitted, and the payer is still charged RC. Never derive vote effects from the presence of a `vote_operation` in a block.
- **Why**: `hf20_vote_evaluator` returns early (`return; // comment already paid`) when the comment has no `comment_cashout_object`, before `update_manabar`, the mana math, `use_mana`, the vote-object create/modify and the virtual-op push; since HF19 the cashout object and all of the comment's `comment_vote_object`s are deleted at payout, so every paid-out mainnet comment takes this path. RC is counted by operation type only.
- **Evidence**: contrib/hive-core/2026-09-05-session-vote-on-paid-out-posts-and-downvote-pool-era.md (item 1, verified); reference/operations.md (vote_operation, Evaluator and Virtual ops); reference/state-objects.md (Key Architectural Notes 5: comment_vote_objects are short-lived); research/hive-core/findings/05-state-objects.md (comment_cashout_object and comment_vote_object Lifecycle); source: libraries/chain/hive_evaluator_social.cpp:620-623, libraries/chain/hive_evaluator_social.cpp:851, libraries/chain/database_comment.cpp:477-481, libraries/chain/database_comment.cpp:366-373, libraries/chain/rc/rc_utility.cpp:799-820
- **Applies**: HF19+ (cashout object removed at payout), HF20+ evaluator path; current: HF28, hived 1.28.7
- **Detect**: indexers that bump vote counts or deduct modelled mana for every `vote_operation` instead of keying off `effective_comment_vote_operation`; UIs that let users vote on posts older than 7 days and display a mana cost; vote bots spending RC on old posts.
- **Wrong**: `for op in block.transactions: if op.type == "vote": apply_vote(op)`.
- **Right**: Derive vote state from `effective_comment_vote_operation` (virtual op 72); before offering a vote, check the comment's `cashout_time` (e.g. `database_api.get_comment_pending_payouts`); expect a non-zero `rc_cost` even for the no-op.

## HC-003: Since HF28 vote cost and strength come from effective vesting shares, with the dust threshold subtracted

- **Rule**: Compute a vote's mana cost and rshares from the voter's effective vesting shares E (own + received - delegated - next power-down step), not from current mana: `used_mana = ceil(E * |weight| * 86400 / 10000 / (vote_power_reserve_rate * 432000))`, so with the current reserve rate of 10 a 100% vote always costs ceil(E/50) = 2% of max mana, for upvotes and downvotes alike, and `rshares = max(0, used_mana - 50,000,000)`. A vote whose `used_mana` is below the dust threshold succeeds, yields 0 rshares and still consumes its full `used_mana`.
- **Why**: HF28 `STABLE_VOTE` replaced the current-mana formula with `get_effective_vesting_shares()`; `HIVE_VOTE_DUST_THRESHOLD` is subtracted and floored at 0 in the HF20+ evaluator (the assert form exists only in `pre_hf20_vote_evaluator`); the downvote gate is a strict `voting + downvote > used_mana` while the upvote gate is `has_mana` (>=), so a zero-stake account can upvote (0 rshares) but not downvote.
- **Evidence**: reference/economics.md (Curation: "Votes to rshares (HF28+ stable vote)"; Notable Design Details: dust threshold is per-vote); contrib/hive-core/2026-09-05-session-vote-on-paid-out-posts-and-downvote-pool-era.md (items 3 and 5, verified); reference/operations.md (vote_operation, Evaluator); research/hive-core/findings/04-chain-evaluators.md (vote_evaluator, "Business Logic - Mana (HF20+)"); reference/hardforks.md (HF28, stable votes); source: libraries/chain/hive_evaluator_social.cpp:659-662, libraries/chain/hive_evaluator_social.cpp:686, libraries/chain/hive_evaluator_social.cpp:692, libraries/chain/hive_evaluator_social.cpp:699, libraries/chain/hive_evaluator_social.cpp:704-707, libraries/protocol/include/hive/protocol/config.hpp:247
- **Applies**: HF28+ for stake-based cost; dust subtraction HF20+; current: HF28, hived 1.28.7
- **Detect**: vote-value estimators that multiply `voting_manabar.current_mana` by the weight; "voting power %" displays that scale vote strength by remaining mana; downvote calculators still applying the pre-HF28 `downvote_pool_percent` scaling; code assuming a tiny vote fails or costs nothing.
- **Wrong**: `rshares = current_mana * weight / 10000 * 86400 / (10 * 432000)` (pre-HF28 model).
- **Right**: `used = ceil(E * weight * 86400 / 10000 / (vote_power_reserve_rate * 432000)); rshares = max(0, used - 50_000_000)`; gate upvotes on `voting_manabar.current_mana >= used` and downvotes on `voting + downvote > used`.

## HC-004: RC is paid by the first operation's required authority, is non-consensus, and floors at zero

- **Rule**: The RC payer of a transaction is the account that provides the first required authority of the first operation that declares one (overrides: `witness_set_properties` charges its owner, `recover_account` charges `account_to_recover`), so order operations with the intended payer first. RC is enforced only when the node is in control (mempool validation, block production, pending reapplication): a block containing an unaffordable transaction is still valid and the payer's mana is drained to exactly 0, never negative. Reducing or removing an RC delegation does not return mana to the delegator.
- **Why**: `resource_user.cpp` resolves the payer deterministically from the first operation; `rc_utility.cpp` branches on `is_processing_block()` and only logs a shortfall there (the `FC_TODO` to make RC consensus has no hardfork assigned); `manabar::use_mana` defaults `min_mana` to `std::numeric_limits<uint64_t>::min()` = 0; the delegation asymmetry is a deliberate anti-"pump" rule.
- **Evidence**: reference/rc.md (Overview: RC payer, non-consensus; Mana Regeneration: "Mana floors at 0"; RC Delegation table: removing delegation does not return mana); research/hive-core/findings/08-resource-credits.md ("RC payer = first operation's required authority"; Key insight 7 pump-prevention asymmetry); research/hive-core/findings/15-rc-consensus.md (Summary; payer resolution with overrides; mana floor discovery); contrib/hive-core/.digested/2026-06-11-zoom14-rc-mana-floor.md; research/hive-core/findings/00-consolidated.md (Notable Finding 1); source: libraries/chain/rc/resource_user.cpp:11-65, libraries/chain/rc/rc_utility.cpp:547-581, libraries/chain/rc/rc_utility.cpp:585, libraries/chain/include/hive/chain/util/manabar.hpp:87-95, libraries/chain/rc/rc_utility.cpp:100-101
- **Applies**: HF20+ (RC system); RC delegation HF26+; current: HF28, hived 1.28.7
- **Detect**: dapps that prepend their own `custom_json` to a user's operations and then expect the user to pay RC (the dapp account pays); indexers or replay tools that treat "insufficient RC" as a reason a block or transaction is invalid; mana models that allow negative balances; delegation managers that "refund" mana to the delegator in their accounting.
- **Wrong**: `ops = [dapp_tracking_custom_json, user_transfer]` with the comment "user pays RC".
- **Right**: Put the user's operation first (or accept that the dapp account is the payer), check `rc_api.find_rc_accounts` for that payer, and clamp any modelled mana at 0.

## HC-005: The mainnet chain id is a literal, not a hash, and signatures bind chain id to the exact wire bytes

- **Rule**: Sign mainnet transactions with the literal 32-byte chain id `beeab0de00000000000000000000000000000000000000000000000000000000` (64 hex chars); never compute `sha256("beeab0de...")`. Only testnet derives its id by hashing (`fc::sha256::hash("testnet")`). The signature digest is `sha256(chain_id || serialized transaction bytes as sent)`, so the bytes you sign must be the bytes you broadcast.
- **Why**: `config.hpp:142` uses the `fc::sha256` hex constructor (fills the digest buffer directly from the hex string, no hashing) while `config.hpp:69` for testnet calls `fc::sha256::hash(...)`; `full_transaction_type::compute_sig_digest()` hashes the chain id plus the exact bytes the transaction arrived in, and either legacy or HF26 packing is accepted (detected by re-packing).
- **Evidence**: contrib/hive-core/.digested/2026-06-16-reviewer-chain-id-constructor-not-hash.md; reference/constants.md (Testnet Overrides, Chain ID row); research/hive-core/findings/01-protocol-foundation.md (Part 01 "Chain ID"; Discovery 15 "Transactions Validate Against Their Actual Wire Bytes; Either Serialization is Accepted"); reference/hardforks.md (HF24, chain ID set); source: libraries/protocol/include/hive/protocol/config.hpp:142, libraries/protocol/include/hive/protocol/config.hpp:69, libraries/chain/full_transaction.cpp:110-116, libraries/chain/full_transaction.cpp:263-284
- **Applies**: HF24+ (Hive chain id); current: HF28, hived 1.28.7
- **Detect**: `sha256("beeab0de")`, `hash(chainId)`, chain-id strings shorter than 64 hex characters, testnet code reusing the mainnet literal, signing code that re-serializes a transaction differently from the broadcast payload.
- **Wrong**: `const CHAIN_ID = sha256("beeab0de0000...0000")`.
- **Right**: `const CHAIN_ID = "beeab0de" + "0".repeat(56)` (or read `chain_id` from `database_api.get_version`), and sign exactly the serialized bytes you broadcast.

## HC-006: Legacy Steem names are still the binary wire format; STM is a key prefix, not an address

- **Rule**: In legacy (binary) serialization HIVE is the symbol `STEEM` and HBD is `SBD` (testnet `TESTS`/`TBD`); blocks and the block_log are packed in legacy mode by default, while API-facing transaction serialization defaults to the HF26 NAI form (`{amount, precision, nai}` with HIVE `@@000000021`, HBD `@@000000013`, VESTS `@@000000037`). condenser_api returns legacy asset strings ("1.000 HIVE") with positional arguments; database_api returns NAI objects with named parameters. The `STM` prefix (`HIVE_ADDRESS_PREFIX`) is prepended to serialized public keys; a Hive "address" is an account name.
- **Why**: `asset_symbol.hpp` keeps `OBSOLETE_SYMBOL_SER` (STEEM) and `OBD_SYMBOL_SER` (SBD) and detects the format on unpack; `serialization_mode_controller::default_pack` is `legacy` for binary and `hf26` for API transactions. The constant name `HIVE_ADDRESS_PREFIX` is a Steem-era misnomer.
- **Evidence**: research/hive-core/findings/01-protocol-foundation.md (Discovery 2 "Legacy Steem Symbol Names Persist in Binary Protocol"; Asset serialization formats); reference/constants.md (Assets table; Misc: `HIVE_ADDRESS_PREFIX`); reference/api.md (Key Notes 1 and 2); contrib/hive-core/.digested/2026-04-10-user-stm-key-prefix-not-address.md; source: libraries/protocol/include/hive/protocol/asset_symbol.hpp:51-53, libraries/protocol/include/hive/protocol/asset_symbol.hpp:157-216, libraries/protocol/include/hive/protocol/misc_utilities.hpp:31-32, libraries/protocol/include/hive/protocol/config.hpp:212
- **Applies**: legacy names at all hardforks; NAI pack type since HF26; current: HF28, hived 1.28.7
- **Detect**: hand-written serializers that put the ASCII bytes `HIVE`/`HBD` into the 8-byte legacy symbol field; parsers that fail on `"STEEM"`/`"SBD"` in block_log or condenser output; code treating `STM...` strings as account identifiers or deriving "addresses" from keys; condenser positional calls mixed with database_api named parameters.
- **Wrong**: `symbol_bytes = b"HIVE" + b"\0" * 3` for a legacy-packed asset; `recipient = "STM" + base58(pubkey)`.
- **Right**: Legacy pack: `STEEM` (precision 3), `SBD` (3), `VESTS` (6); NAI pack: `@@000000021`, `@@000000013`, `@@000000037`; recipients are account names (3-16 characters).

## HC-007: Transaction size is capped at 64 KB with no operation-count limit; expiration is 1 h, or up to 24 h since HF28 with a 1 h runtime cap

- **Rule**: Keep the serialized transaction at or under `HIVE_MAX_TRANSACTION_SIZE` = 65,536 bytes; there is no explicit maximum number of operations (only `operations.size() > 0` is checked). Set `expiration` no more than 1 hour (3,600 s) after head block time before HF28; since HF28 (`EXPIRATION_TIME`) the field may be up to 24 hours (86,400 s) ahead, but a node caps the transaction's runtime validity at `min(expiration, now + 1 h)` from its first validation (the dedupe index keeps the original expiration for the full window).
- **Why**: `transaction::validate()` only requires a non-empty operation list; the size limit is a protocol constant that is also the floor of the witness-voted block size. `database::validate_transaction()` asserts `expiration <= now + HIVE_MAX_TIME_UNTIL_SIGNATURE_EXPIRATION` after HF28 (otherwise `+ HIVE_MAX_TIME_UNTIL_EXPIRATION`) and sets the runtime expiration once per transaction object.
- **Evidence**: reference/constants.md (Block / Transaction Limits; Timing: `HIVE_MAX_TIME_UNTIL_EXPIRATION`, `HIVE_MAX_TIME_UNTIL_SIGNATURE_EXPIRATION`); reference/README.md (Important Non-Obvious Facts: no max operations per transaction); research/hive-core/findings/00-consolidated.md (Open Question 18); research/hive-core/findings/09-hardfork-history.md (HF28 sub-feature `EXPIRATION_TIME`); reference/hardforks.md (HF28: extended signature expiration up to 24h); source: libraries/protocol/include/hive/protocol/config.hpp:364, libraries/protocol/transaction.cpp:40-56, libraries/protocol/include/hive/protocol/config.hpp:232-233, libraries/chain/database.cpp:2536-2548 (confirmed in the pinned worktree), libraries/chain/database.cpp:2683-2684 (confirmed in the pinned worktree)
- **Applies**: 64 KB and no operation limit at all hardforks; 24 h expiration HF28+; current: HF28, hived 1.28.7
- **Detect**: batchers that split transactions by operation count without a serialized-size check; clients setting `expiration = now + 2h` on pre-HF28 assumptions or `now + 48h` now; retry loops that re-broadcast an expired transaction unchanged; pre-signed flows that assume a 24 h expiration keeps the transaction alive in a mempool for 24 h.
- **Wrong**: `if len(ops) > 100: split()` with no size check; `expiration = head_time + 7200` before HF28 (rejected with `transaction_expiration_exception`).
- **Right**: `assert len(serialize(tx)) <= 65536`; `expiration = head_time + 60..3600` for normal use; up to `+ 86400` only for deliberately pre-signed transactions, knowing a node treats them as expired 1 h after it first validated them.

## HC-008: Authorities hold at most 40 members and account_auths are followed only two hops deep

- **Rule**: An authority may contain at most 40 keys plus accounts (`HIVE_MAX_AUTHORITY_MEMBERSHIP`); nested `account_auths` are resolved only to `HIVE_MAX_SIG_CHECK_DEPTH` = 2 (keys held by an account two hops away still count, but `account_auths` encountered at depth 2 are silently skipped, not rejected); at most 125 distinct accounts (`HIVE_MAX_SIG_CHECK_ACCOUNTS`) are visited in one check. These limits live in signature verification, not in `validate()`, and the 40/125 caps are enforced only for blocks after HF20.
- **Why**: `sign_state::check_authority_impl` checks `key_auths` at every depth but `continue`s past `account_auths` when `depth == limits.recursion`, and counts membership and visited accounts; the chain passes `HIVE_MAX_SIG_CHECK_DEPTH = 2` always and the 40/125 limits as 0 (unlimited) before HF20. `authority::validate()` only checks account-name format.
- **Evidence**: reference/constants.md (Account Creation: `HIVE_MAX_AUTHORITY_MEMBERSHIP`, `HIVE_MAX_SIG_CHECK_DEPTH`, `HIVE_MAX_SIG_CHECK_ACCOUNTS`); research/hive-core/findings/00-consolidated.md (Open Question 20); research/hive-core/findings/01-protocol-foundation.md (Multi-sig; Verification Algorithm); research/hive-core/findings/03-operation-validation.md (authority validation notes; chain-level checks table); source: libraries/protocol/include/hive/protocol/config.hpp:357, libraries/protocol/include/hive/protocol/sign_state.hpp:216-223, libraries/protocol/include/hive/protocol/sign_state.hpp:226-233, libraries/chain/database.cpp:2620-2622
- **Applies**: depth limit at all hardforks; 40-member and 125-account caps HF20+; current: HF28, hived 1.28.7
- **Detect**: multisig or "guardian" designs with three or more levels of account delegation; authority builders without a 40-entry cap; tests that expect `validate()` to reject deep or oversized authorities.
- **Wrong**: Account `treasury` whose only auth is account `council`, whose only auth is account `board`, whose only auth is account `audit` holding the keys: `audit` is a third hop, never visited, so the transaction fails as unauthorized although every `validate()` passes.
- **Right**: Keep signing keys within two account hops (`treasury` -> `council` -> `board` with the keys in `board`), cap each authority at 40 members, and keep the whole authority graph under 125 accounts.

## HC-009: Comment and vote state is ephemeral; capture it from operations, never from old state

- **Rule**: Do not expect hived to serve votes, permlinks, beneficiaries or payout settings for a comment after its 7-day cashout. `comment_object` stores only a RIPEMD-160 hash of `permlink@author_id`; the `comment_cashout_object` (permlink string, rshares, beneficiaries, options) and every `comment_vote_object` are deleted at payout, and paid-out comments are archived to RocksDB as `{comment_id, parent_comment, depth}` keyed by that hash. Indexers must record content from `comment_operation` and vote effects from `effective_comment_vote_operation` as they occur.
- **Why**: `process_comment_cashout` removes the cashout object (HF19+) and bulk-removes the comment's votes; the default `comment-archive = ROCKSDB` option moves paid-out comments out of chainbase once irreversible. Lookups by author+permlink still resolve through the hash, but there is no permlink string or vote data left to return.
- **Evidence**: reference/README.md (Important Non-Obvious Facts: comment permlinks lost after cashout); reference/state-objects.md (comment_object Note and Archive; comment_cashout_object; Key Architectural Notes 2, 3, 5); research/hive-core/findings/05-state-objects.md (comment_cashout_object and comment_vote_object Lifecycle); research/hive-core/findings/13-external-storage.md (archive record contents; APIs that resolve author+permlink); source: libraries/chain/database_comment.cpp:366-373, libraries/chain/database_comment.cpp:477-481, libraries/chain/include/hive/chain/detail/state/comment_object.hpp:92-96, libraries/chain/external_storage/rocksdb_comment_archive.cpp:143-172
- **Applies**: HF19+ (cashout object removal); RocksDB archive default since hived 1.28; current: HF28, hived 1.28.7
- **Detect**: `condenser_api.get_active_votes` or `database_api.get_comment_pending_payouts` used as a data source for posts older than 7 days; backfill jobs that rebuild vote history from node state; code assuming `comment_object` carries author or permlink strings.
- **Wrong**: `votes = condenser_api.get_active_votes(author, permlink)` for a two-year-old post, expecting its historical voters.
- **Right**: Stream blocks (or `account_history_api.enum_virtual_ops`) and persist `comment_operation`, `effective_comment_vote_operation`, `author_reward_operation`, `curation_reward_operation` and `comment_benefactor_reward_operation` as they appear; use state queries only inside the cashout window.

## HC-010: delete_comment and comment_options have strict one-way preconditions

- **Rule**: `delete_comment_operation` fails if the comment has replies, has `net_rshares > 0` (HF19+ hard error) or has already paid out; a voted post cannot be deleted, only edited. `comment_options_operation` can only make settings more restrictive (lower `max_accepted_payout`, lower `percent_hbd`, disable votes or curation rewards), beneficiaries can be set once and only before any vote (max 8 as an in-control soft-fork limit), and applying options to a paid-out comment is a hard error since HF24. Send `comment_options` in the same transaction as the `comment_operation` that creates the post.
- **Why**: `delete_comment_evaluator` requires a cashout object, no replies and non-positive net rshares (pre-HF19 a voted delete was a silent no-op with `ineffective_delete_comment_operation`); `comment_options_evaluator` enforces the ratchet through `configure_options()`, requires no existing votes when reducing rewards, and `add_beneficiary()` is accepted only before votes.
- **Evidence**: reference/operations.md (delete_comment_operation; comment_options_operation); research/hive-core/findings/04-chain-evaluators.md (delete_comment_evaluator; comment_options_evaluator); reference/constants.md (Misc: `HIVE_MAX_COMMENT_BENEFICIARIES` = 8); source: libraries/chain/hive_evaluator_social.cpp:55-106, libraries/chain/hive_evaluator_social.cpp:108-172
- **Applies**: HF19+ (hard delete rejection), HF24+ (paid-out comment_options hard error); current: HF28, hived 1.28.7
- **Detect**: "delete post" buttons with no check for votes, replies or payout; publishing flows that broadcast the comment first and the beneficiaries or payout settings in a later transaction; code that tries to raise `max_accepted_payout` or re-enable votes.
- **Wrong**: `broadcast([comment_op]); broadcast([comment_options_op])` (a vote can land in between and the options then fail), or deleting a post that has an upvote.
- **Right**: `broadcast([comment_op, comment_options_op])` in one transaction; offer "edit to empty" instead of delete for voted or replied posts; only ever lower payout settings.

## HC-011: Governance power is delayed 30 days after power-up and expires after 365 idle days

- **Rule**: VESTS received through `transfer_to_vesting` count immediately for RC, content-vote mana and delegation, but contribute nothing to witness or DHF proposal votes for 30 days (buffered in `delayed_votes`, matured per block with `delayed_voting_operation`). All of an account's governance votes (witness and proposal) are removed after 365 days without a governance action; any `account_witness_vote`, `account_witness_proxy` or `update_proposal_votes` refreshes the timer. Setting a proxy clears the account's own witness votes, an account may vote for at most 30 witnesses, and a proxy chain is at most 4 deep. Governance weight is `vesting_shares - sum_delayed_votes + proxied votes`, not `vesting_shares`.
- **Why**: the HF24 `transfer_to_vesting` evaluator bypasses `create_vesting2` (which grants immediate vote power on every other vesting path) and registers a delayed bucket instead; `remove_expired_governance_votes()` runs at end of block on `governance_vote_expiration_ts` (`HIVE_GOVERNANCE_VOTE_EXPIRATION_PERIOD` = 365 days, HF25); the proxy and witness-vote evaluators enforce the 30-vote and depth-4 limits and clear votes on proxy change.
- **Evidence**: research/hive-core/findings/14-delayed-voting.md (Summary; Key Discovery 1 "The delay applies ONLY to transfer_to_vesting"); reference/state-objects.md (account_object: `delayed_votes`, `governance_vote_expiration_ts`, `get_governance_vote_power()`); research/hive-core/findings/07-economic-model.md (DHF: Governance vote expiration); research/hive-core/findings/04-chain-evaluators.md (remove_expired_governance_votes; account_witness_proxy_evaluator; account_witness_vote_evaluator); reference/operations.md (account_witness_vote_operation; account_witness_proxy_operation; transfer_to_vesting_operation); source: libraries/chain/hive_evaluator_transfer.cpp:311-317, libraries/chain/database_vesting_helpers.hpp:29-30, libraries/protocol/include/hive/protocol/config.hpp:175, libraries/chain/database.cpp:2352 (confirmed in the pinned worktree; the KB cites :2353 and :2349), libraries/chain/hive_evaluator.cpp:210-261, libraries/chain/hive_evaluator.cpp:264-326
- **Applies**: delayed voting HF24+; vote expiration HF25+; 30-vote limit HF2+; current: HF28, hived 1.28.7
- **Detect**: witness or proposal ranking code that sums `vesting_shares` (or HP) directly; dashboards that show full governance weight right after a power-up; monitoring that treats a vanished witness vote as a user action; UIs that let an account with a proxy also pick witnesses.
- **Wrong**: `witness_weight[w] += account.vesting_shares` for each voter.
- **Right**: `weight = vesting_shares - sum_delayed_votes + proxied_vsf_votes` (or read `witness_object.votes` / `proposal_object.total_votes` from the node), and remind users to refresh governance votes before 365 days elapse.

## HC-012: Inclusion in a block is not finality; wait for the last irreversible block

- **Rule**: Treat a transaction as final only when its block number is at or below the node's last irreversible block (`database_api.get_dynamic_global_properties().last_irreversible_block_num`, or `transaction_status_api.find_transaction` reporting `within_irreversible_block`). `broadcast_transaction_synchronous` returning `{block_num, trx_num}` means inclusion in a reversible block, and `broadcast_transaction` means only mempool acceptance. A block becomes irreversible once 16 of the 21 scheduled witnesses (75%) have approved it, implicitly by producing on top of it or explicitly via HF26 fast-confirm; reorgs are bounded by head - LIB (normally a few blocks; hard cap 1,024 blocks, about 51 minutes).
- **Why**: `update_last_irreversible_block` requires `num_witnesses - (25% * num_witnesses)` = 16 approvals; fast-confirm transactions are processed out of band and can advance LIB between blocks; blocks above LIB keep undo sessions and can be popped on a fork switch, blocks at or below LIB are written to the block log and cannot be reverted.
- **Evidence**: reference/consensus.md (Irreversibility; Fork Resolution); reference/api.md (condenser_api Broadcast; transaction_status_api; network_broadcast_api); research/hive-core/findings/06-consensus-mechanisms.md (Last Irreversible Block (LIB) Calculation; Fork Database maximum size); research/hive-core/findings/10-api-layer.md (Transaction Broadcast; transaction_status_api status enum); source: libraries/protocol/include/hive/protocol/config.hpp:381, libraries/chain/database.cpp:2996, libraries/chain/database.cpp:3017, libraries/chain/include/hive/chain/fork_database.hpp:67, libraries/plugins/apis/database_api/include/hive/plugins/database_api/database_api_objects.hpp:218 (confirmed in the pinned worktree)
- **Applies**: all hardforks (fast-confirm HF26+); current: HF28, hived 1.28.7
- **Detect**: deposit crediting or order fulfilment triggered by `broadcast_transaction_synchronous` success, by `block_num <= head_block_number`, or by a fixed "wait N blocks" delay; indexers that write irreversible tables from head blocks without reorg handling.
- **Wrong**: `result = broadcast_transaction_synchronous(tx); credit_user(result.block_num)`.
- **Right**: `credit_user()` only when `result.block_num <= dgpo.last_irreversible_block_num` (poll), or when `find_transaction(id).status == "within_irreversible_block"`; index reversible blocks with rollback support.
