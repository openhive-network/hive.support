# Findings: rc-consensus

Deep-dive into the boundary between the Resource Credits subsystem and consensus in hive-core at release `1.28.6` (`10ac0ce94f7591b6ad80db1a23d046c9d57b6559`). Builds on Part 08 (Resource Credits), which covers RC mechanics broadly; this part focuses on *where exactly RC touches consensus*: enforcement contexts, integration points in the transaction/block pipelines, the `delegate_rc` exception-handling machinery, and the determinism discipline that keeps RC state identical across nodes despite not being consensus-enforced.

## Summary

RC at 1.28.6 is "shadow consensus": since the 1.27-era move from a plugin into `libraries/chain/`, all RC state lives in chainbase and is updated by strictly deterministic, block-time-driven code on every node — but a payer's mana shortfall aborts a transaction only when the node is *in control* (validating a new standalone tx, producing a block) or reapplying pending transactions; during block application and replay the shortfall is merely logged (HF26+) and the payer's mana is floored at zero. Even `delegate_rc` (chain-interpreted since HF26, and whose validity *reads* RC mana state) cannot invalidate a block: `custom_json_evaluator` swallows all interpreter exceptions outside in-control contexts, with a dedicated nested undo session guaranteeing atomic rollback of the failed custom op. The single hard bridge to consensus is the `resource_new_accounts` pool, which is force-overwritten every block with the consensus-enforced `dgpo.available_account_subsidies` value.

## Key Discoveries

### 1. The enforcement decision is a function of six node states, not "mempool vs block"
- **What**: `use_account_rcs` throws `not_enough_rc_exception` iff `db.is_in_control() || db.is_reapplying_one_tx()`. `is_in_control()` = `is_validating_one_tx() || is_producing_block()` (`database.hpp:173`). Block application from P2P (`TX_STATUS_P2P_BLOCK`), replay (`TX_STATUS_BLOCK`), and pending reapplication (`TX_STATUS_PENDING`) are *not* in control; only the first two of those get the permissive accept-and-log path, while pending reapplication throws.
- **Where**: `libraries/chain/rc/rc_utility.cpp:547-583`, `libraries/chain/include/hive/chain/database.hpp:143-173`
- **Impact**: "RC is enforced at mempool only" is approximately right but loses three distinctions that matter: (a) a producing witness *does* enforce RC when assembling a block; (b) pending transactions are re-checked after every block and dropped if they no longer afford (behavior introduced Oct 2024, commit `26ac90c5d`); (c) a block arriving from P2P is *never* RC-enforced, no matter how it was produced.

### 2. RC mana cannot go negative — it floors at zero (corrects Part 08 and reference/rc.md)
- **What**: `manabar::use_mana( int64_t mana_used, int64_t min_mana = std::numeric_limits<uint64_t>::min() )` — `uint64_t`'s `min()` is **0**, so the default floor is 0: `current_mana = signed_sat_sub(...); if (current_mana < min_mana) current_mana = min_mana;`. The only RC consumption call is `acc.rc_manabar.use_mana( rc + surcharge )` with the default floor (`rc_utility.cpp:585`). A payer included in a block without enough mana ends at exactly 0, not in debt. The delegation paths likewise clamp at 0 (`rc_utility.cpp:381`) or are pre-guarded against negative (`rc_utility.cpp:96-104`).
- **Where**: `libraries/chain/include/hive/chain/util/manabar.hpp:87-95`, `libraries/chain/rc/rc_utility.cpp:585`
- **Impact**: Part 08 ("Mana can go negative via use_mana", line 364) and `reference/rc.md` ("Mana can go negative") state the opposite. The economic consequence is real: an account drained in-block restarts regeneration from 0, not from a negative balance, so the worst-case penalty of a witness force-including an unaffordable tx is bounded. (Note `std::numeric_limits<uint64_t>::min()` reads like a typo for `int64_t` lowest, but it is load-bearing as a zero floor.) Contrib note filed: `contrib/hive-core/2026-06-11-zoom14-rc-mana-floor.md`.

### 3. delegate_rc failures never invalidate blocks — exception swallowing + nested undo session
- **What**: All `rc_custom_operation` processing runs inside `custom_json_evaluator::do_apply`'s try/catch: `catch (fc::exception) { if (_db.is_in_control()) throw; }` — otherwise the exception is silently swallowed (`hive_evaluator.cpp:361-368`). Atomicity of the half-applied custom op is guaranteed by `generic_custom_operation_interpreter::apply_operations`, which opens its own undo session and only `squash()`es on success (`generic_custom_operation_interpreter.hpp:186,224`; the comment cites issue #256).
- **Where**: `libraries/chain/hive_evaluator.cpp:337-373`, `libraries/chain/include/hive/chain/generic_custom_operation_interpreter.hpp:184-251`
- **Impact**: This resolves the question Part 08 leaves open: since HF26 the `delegate_rc` evaluator contains FC_ASSERTs that read RC mana state unconditionally (insufficient-RC at `rc_utility.cpp:96`, delegate-0-on-create at `:66`, same-amount at `:71`) — yet none of them can reject a block, because in any block context the whole custom op is rolled back and the containing transaction (and its other operations) stands. RC state therefore influences *state evolution* (whether a delegation took effect) but never *block validity*. All nodes still converge because the asserts fire identically everywhere (inputs are deterministic chainbase state).

### 4. Producer/validator symmetry: a generated block is re-applied "as if from P2P"
- **What**: During block production transactions run under `TX_STATUS_GEN_BLOCK` in a throwaway pending session that is reset after assembly (`block_producer.cpp:135-215`); the assembled block is then applied through `database::apply_block_extended`, which unconditionally sets `TX_STATUS_P2P_BLOCK` — "Note that we're treating the block as completely new" (`database.cpp:2123-2130`). RC per-block bookkeeping (`block_info.add`, pending stats) is only accumulated when `is_validating_block() || is_replaying_block()` (`rc_utility.cpp:821-830`), i.e. *not* during generation.
- **Where**: `libraries/chain/database.cpp:2123-2142`, `libraries/plugins/witness/block_producer.cpp:111-216`, `libraries/chain/rc/rc_utility.cpp:821-830`
- **Impact**: Pool levels, usage buckets, weights, and RC stats are derived exclusively from the canonical block-application pass, so the producer and every validator compute identical RC pool state. Without the re-application step, the GEN_BLOCK exclusion would desynchronize the producer's pools from the network.

### 5. The one hard consensus coupling: `resource_new_accounts` pool is slaved to `available_account_subsidies`
- **What**: `finalize_block` computes the new_accounts pool like any other, then discards the result in favor of the consensus value: `new_pool = dgpo.available_account_subsidies` whenever they differ, logging the adjustment (`rc_utility.cpp:770-779`). The consensus pool itself regenerates each block via `rd_apply` in `process_subsidized_accounts` (`database.cpp:1819-1833`) and is decremented by subsidized `claim_account` under *unconditional* consensus asserts — global pool check `hive_evaluator_account.cpp:441-445`, plus elected-witness-only and per-witness pool checks when in a block (`:425-440`).
- **Where**: `libraries/chain/rc/rc_utility.cpp:770-779`, `libraries/chain/hive_evaluator_account.cpp:425-445`, `libraries/chain/database.cpp:1819-1833`
- **Impact**: Subsidized account creation is the only resource where exceeding the budget is a hard block-validity rule — enforced by the consensus twin, not by RC. The RC pool passively mirrors it so RC *pricing* of subsidized accounts tracks the consensus pool level. Witness-voted subsidy params flow in via `rd_setup_dynamics_params` (`witness_schedule.cpp:138-144`) and are pushed into RC params on schedule changes (`witness_schedule.cpp:438` → `set_pool_params`, `rc_utility.cpp:833-851`), regenerating the new_accounts price curve with pure integer math (`rc_curve.cpp:32-98`).

### 6. RC state evolution is deterministic by careful design — a checklist of mechanisms
- **What**: Everything that feeds RC state is consensus-derived: regeneration timestamps use `dgpo.time`/`head_block_time()` (block timestamps, never wall clock — e.g. `rc_utility.cpp:503,46,609`); execution-time costs are fixed benchmark constants compiled in (`resource_sizes.cpp`, `USE_FIXED_SIZE`); state sizes are hardcoded; plugin-dependent state (account `json_metadata`) is deliberately *excluded* from both counting and differential discount because its presence depends on the optional `metadata` plugin (`resource_count.cpp:63-65,83-85,205-207`); object-removal batching reads `dgpo.current_remove_threshold` — consensus state, default `HIVE_GLOBAL_REMOVE_THRESHOLD` = 200 (mainnet), settable only by tests (`database.cpp:458-469`, `global_property_object.hpp:164`, `config.hpp:178`); and the witness-driven runtime regeneration of curve params uses integer-only math (`rc_curve.cpp`), unlike the build-time Python float pipeline (`rc_generate_resource_parameters.py`) whose output is frozen into the binary.
- **Where**: as cited per item
- **Impact**: This corrects the framing in Part 00 ("RC state is time-dependent (continuous mana regeneration) making deterministic cross-node consensus hard", line 21): regeneration is lazy but driven entirely by block time, so RC state *is* deterministic across same-binary nodes. The actual obstacles to making RC consensus are different: historical blocks containing RC-violating transactions (replay would fail under retroactive enforcement), cost constants becoming de-facto consensus parameters frozen per-binary, and warning-only invariants that would need to become asserts (the `FC_TODO` at `rc_utility.cpp:545-546` plus `NOTIFYALERT` wlogs at `:340,369,394`).

### 7. Every consensus path that changes VESTS must bracket the change with RC calls — full inventory
- **What**: The contract is `regenerate_rc_mana(account, now)` *before* the VESTS change and `update_account_after_vest_change(account, now, fill, check_overflow)` *after*. Missed brackets are detected at runtime: mainnet `wlog("NOTIFYALERT! ...")`, testnet (`USE_ALTERNATE_CHAIN_ID`) hard assert (`rc_utility.cpp:331-343,365-376,390-400`). `account_object.last_max_rc` exists solely to catch drift — "can be removed once RC becomes part of consensus" (`detail/state/account_object.hpp:218`).
- **Where**: call sites — `withdraw_vesting_evaluator` (`hive_evaluator_transfer.cpp:346,388`; `fill=false` so canceling power-down cannot pump mana), `claim_reward_balance_evaluator` (`:655,663`), `delegate_vesting_shares_evaluator` (`:692-693,901-902`, both parties, overflow-checked), `database::adjust_account_vesting_balance` (`database.cpp:1017,1022` — covers transfer_to_vesting and reward vesting), `clear_null_account_balance` (`:1218,1226`), `clear_account` (`:1494,1509,1525,1566` — HF23 clears, overflow-checked), `clear_expired_delegations` (`:3129,3135` — returning VEST delegations), `process_vesting_withdrawals` (`database_vesting.cpp:192,204,247,276` — weekly power-down, overflow-checked on the from-account), debug plugin via `update_rc_for_custom_action` (`debug_node_plugin.cpp:317`, `rc_utility.cpp:469-476`).
- **Impact**: This is the maintenance burden RC imposes on consensus code: any new evaluator or per-block process that touches VESTS must add the bracket or it produces NOTIFYALERT drift on mainnet and assertion failures on testnet. The `_check_for_rc_delegation_overflow=true` variant is required wherever an account can *lose* effective VESTS (power-down, delegation out, account clears), because RC delegations backed by vanished VESTS must be reclaimed (`rc_utility.cpp:403-443`).

### 8. Flood control is a node-local surcharge layer on top of RC, with witness escape hatches at both ends
- **What**: When `_pending_tx_size / dgpo.maximum_block_size > flood_level` (default 20 blocks), new and reapplied transactions pay `surcharge = (blocks_over) × flood_surcharge × cost / 10000` (defaults: `rc_utility.cpp:24-25`; config `rc-flood-level` / `rc-flood-surcharge`, `chain_plugin.cpp:1508-1509,1820-1821`). Computed only when `is_validating_one_tx() || is_reapplying_one_tx()` (`rc_utility.cpp:506`) — never part of block-context accounting. Single-op transactions carrying `feed_publish` / `witness_update` / `witness_set_properties` from a currently *elected* witness are exempt (`:514-527`) and additionally marked privileged (`full_transaction.hpp:91,132`), which re-queues them at the *front* of the pending list via the fork-recovery `_popped_tx` mechanism (`database.cpp:642-647`).
- **Where**: `libraries/chain/rc/rc_utility.cpp:505-538`, `libraries/chain/database.cpp:642-647`, `libraries/plugins/chain/chain_plugin.cpp:1504-1509`
- **Impact**: Two nodes with different flood settings can legitimately disagree about mempool admission — this is fine precisely because RC cost is not consensus. Witness ops stay deliverable under flood both by being surcharge-exempt and by jumping the queue, so the chain can raise `maximum_block_size` (or fix feeds) to resolve congestion. Pending transactions that can no longer pay (base or surcharged) are dropped at reapplication (`db_with.hpp:133-136`, counted as `failed_txs`); mempool is additionally bounded by `max-mempool-size` (default 100M, `chain_plugin.cpp:1507`) and the 200 ms reapplication time budget (`HIVE_PENDING_TRANSACTION_EXECUTION_LIMIT`, `config.hpp:423`, `db_with.hpp:108-110`).

### 9. Custom-op parsing is two-mode: strict for in-control, lenient for blocks
- **What**: `custom_json_operation.json` for id `"rc"` is parsed with `format_validation_mode::full` when in control, `relaxed` otherwise (`generic_custom_operation_interpreter.hpp:231`); UTF-8 truncation verification is disabled outside control (`hive_evaluator.cpp:353-357`). Structurally wrong-but-parseable variants (array size ≠ 2, extra fields) assert only in control — in blocks they log "Incomplete/Dangling custom operation ignored" and proceed with whatever parsed (`generic_custom_operation_interpreter.hpp:88-125`). Inner ops are `validate()`d and must require *exactly* the same authority sets as the outer custom_json (`:200-211`), all inside the swallowed-exception zone.
- **Where**: `libraries/chain/include/hive/chain/generic_custom_operation_interpreter.hpp:59-143,184-251`
- **Impact**: A malformed `"rc"` custom_json is rejected at the API/mempool boundary but tolerated (as a no-op) inside a block — the same asymmetric philosophy as mana enforcement, applied at the parse layer. This is what makes it safe for the chain to interpret a custom_json id at all without a hardfork-style validity cliff.

### 10. HF26 turned `delegate_rc` from dead letter to active, with a deliberate one-sided gate
- **What**: Pre-HF26 the evaluator returns early (`dlog "Ineffective RC delegation"`, `rc_utility.cpp:29-33`) — the op parses, costs custom_json RC, but does nothing. Post-HF26 it executes; its `is_in_control()`-gated asserts (minimum delegation = `account_creation_fee/3` in VESTS `:38-44`; no new delegations while expired-delegation cleanup pending `:49`) are policy-only, while its unconditional asserts (`:66,71,96`) are state-integrity rules that, per Discovery 3, still cannot break blocks. The extra RC usage of the inner op is collected by the evaluator itself (`handle_custom_op_usage`, `:110`; `resource_count.cpp:672-678`) because by `finalize_transaction` time the JSON would otherwise need re-interpretation.
- **Where**: `libraries/chain/rc/rc_utility.cpp:27-111`
- **Impact**: The HF26 gate is the template for chain-interpreting custom ops: hardfork-gate the *effect*, never the *parseability*, and keep every failure swallowed outside control. Note there was no HF26 state migration for RC delegations (`database_hardfork.cpp:496-509` creates only the future witness schedule object) — the delegation indices simply start empty.

## The RC↔Consensus boundary in detail

### Node-state predicates and what RC does in each

`database.hpp:143-173` defines the state lattice (`TX_STATUS_*`); RC behavior keyed to it:

| Context | Predicate | `use_account_rcs` on shortfall | Flood surcharge | `delegate_rc` failure | RC stats/`block_info` |
|---|---|---|---|---|---|
| New tx from API/P2P | `is_validating_one_tx()` (in control) | throw `not_enough_rc_exception` → tx rejected | yes | throws → tx rejected | not collected |
| Reapplying pending after block/fork | `is_reapplying_one_tx()` | throw → tx **dropped** from mempool (`db_with.hpp:133-136`) | yes | swallowed → tx survives, delegation skipped | not collected |
| Producing a block | `is_producing_block()` (in control) | throw → tx skipped, stays pending (`block_producer.cpp:199-207`) | no | throws → tx skipped, stays pending | not collected |
| Validating block from P2P (incl. own generated, forks) | `is_validating_block()` | accept; `ilog "Accepting transaction..."` if HF26 (`rc_utility.cpp:564-581`); mana floored at 0 | no | swallowed, rolled back | collected |
| Replaying irreversible blocks | `is_replaying_block()` | accept; same log path | no | swallowed, rolled back | collected |

Mempool-shortfall messages distinguish the surcharge case: if base cost is affordable but cost+surcharge is not, the error tells the user to wait / power up / ask witnesses for bigger blocks (`rc_utility.cpp:549-556`).

A payer-less transaction (no required authorities in any op) asserts only in control; in blocks it simply doesn't charge anyone (`rc_utility.cpp:480-486`). Payer resolution is the first required authority of the first op, with explicit overrides for `witness_set_properties` (owner), `recover_account` (account_to_recover), and `witness_block_approve` (witness) (`resource_user.cpp:11-65`).

### Transaction pipeline integration

Order inside `database::_apply_transaction` (`database.cpp:2618-2702`):

1. `notify_pre_apply_transaction` → `rc().reset_tx_info(trx)` (`:2689`) — zeroes `tx_info`, resolves payer, records single-op tag (`rc_utility.cpp:853-859`).
2. Per operation, `database_impl::apply_operation` (`:2722-2746`): if HF20+, `rc().handle_operation_discount<operation>(op)` *before* the evaluator (`:2737-2738`) — accumulates negative `state_bytes` usage for state about to be replaced (account/witness authority updates, recover_account, existing rc delegations; `resource_count.cpp:17-168`). For `delegate_rc`, the evaluator additionally self-reports discount and extra usage (`rc_utility.cpp:35,110`).
3. After all ops, `rc().finalize_transaction(full_tx)` (`:2699`, HF20-gated at `rc_utility.cpp:801`): `count_resources` over the signed tx (sizes, expiration-scaled tx base, signature-scaled verify time; `resource_count.cpp:582-631`), `compute_cost` (per-resource price curve over current pools; `rc_utility.cpp:286-316`), `full_tx.set_rc_cost(total)`, then `use_account_rcs(total)` which regenerates and debits the payer; privileged status propagates to `full_tx.set_privilege()` (`rc_utility.cpp:813-819`).
4. Only when validating/replaying a block: `block_info.add(tx_info)` and pending-stats accumulation (`:821-830`).

Note `finalize_transaction` runs *inside* the transaction's `FC_CAPTURE_AND_RETHROW` — an exception here fails the transaction, and in a block context would fail the **block**. The RC code is therefore written to be exception-free on the block path: the surcharge overflow assert sits behind the mempool-only branch (`rc_utility.cpp:506,534`), `compute_cost`'s `FC_ASSERT(rc_regen > 0)` is pre-guarded by the caller (`:257,298,307`), and the one genuinely reachable throw — `FC_ASSERT(op.end_date > _now)` for `create_proposal` in the counting visitor (`resource_count.cpp:488`) — is shadowed by the DHF evaluator's identical strict check earlier in the same transaction (`dhf_evaluator.cpp:43`). See Discrepancies #5.

### Block pipeline integration

Order inside `database::_apply_block` (`database.cpp:2183-2369`):

1. `rc().reset_block_info()` immediately after `notify_pre_apply_block` (`:2191`).
2. Transactions apply (accumulating `block_info` per above), then the per-block processes (`:2330-2351`), then RC's two block-level steps right before `process_hardforks()`:
   - `rc().handle_expired_delegations()` (`:2353`; `rc_utility.cpp:598-637`) — continues clearing RC-delegation overflow from previous blocks, oldest `rc_expired_delegation_object` first, bounded by `remove_guard(get_remove_threshold())`.
   - `rc().finalize_block()` (`:2354`; `rc_utility.cpp:734-797`, HF20-gated) — per resource: record budget, `decay = rd_compute_pool_decay(params, pool - usage, 1)` (decay applies to the post-usage pool), rotate the 24×1h usage buckets (`HIVE_RC_BUCKET_TIME_LENGTH`/`HIVE_RC_WINDOW_BUCKET_COUNT`, `config.hpp:483-484`), `new_pool = pool - decay + budget - usage` clamped at ≥0, new_accounts pool overwritten from consensus (Discovery 5), then `recalculate_resource_weights` (`rc_objects.hpp:81-95`) and the daily stats rotation/report (`handle_auto_report`, `rc_utility.cpp:679-715`; frequency `HIVE_BLOCKS_PER_DAY` on mainnet, `config.hpp:487-489`).
3. RC state participates in the block's undo session like all chainbase state (`apply_block_extended`, `database.cpp:2132-2141`), so fork switches rewind RC state consistently — including across the fork boundary, since popped blocks' transactions land in `_popped_tx` and re-validate under `TX_STATUS_PENDING`.

### HF20 genesis of RC state

`database_hardfork.cpp:366-414` (inside `case HIVE_HARDFORK_0_20`): params loaded from the build-time-compiled jsonball (`hive::jsonball::get_resource_parameters()`; source `libraries/jsonball/data/resource_parameters.json`, transform `programs/build_helpers/hive_build_helpers/rc_generate_resource_parameters.py`, wiring `libraries/jsonball/CMakeLists.txt:28-30`); new_accounts params immediately overridden from the witness schedule (`set_pool_params`, `:386`); 24 buckets created with back-dated timestamps (`:389-395`); pools start at `pool_eq` (`rc_objects.hpp:48-59`); pending+archive stats objects created (`:400-401`); every existing account gets `rc_adjustment = HIVE_RC_HISTORICAL_ACCOUNT_CREATION_ADJUSTMENT` (2020748973 ≈ 1.000 HIVE in VESTS at HF20, `config.hpp:492`) and a full mana bar (`:403-414`). Post-HF20 accounts get `rc_adjustment` from the actual creation fee at creation time (`hive_evaluator_account.cpp:144-153`). The custom-op interpreter for `"rc"` is registered unconditionally at database open (`database_init.cpp:37` → `rc_utility.cpp:717-732`), so even pre-HF26 blocks parse `"rc"` custom_jsons (leniently, per Discovery 9).

### What it would take to flip the switch

The intended migration is written in the code: add `|| db.has_hardfork(X)` to the enforcement condition and convert NOTIFYALERT warnings to asserts (`rc_utility.cpp:545-546`). The hidden prerequisites visible from this zoom: replay of pre-X history must keep the permissive path (the condition as written does this naturally — enforcement would start at X); the per-binary cost constants (`resource_sizes.cpp` under `USE_FIXED_SIZE`) become consensus parameters, so any rebuild that changes them becomes a hardfork; the `custom_json_evaluator` swallow would presumably stay (it predates RC and protects all custom-op ids), meaning `delegate_rc` would *still* not affect block validity — only the mana debit in `use_account_rcs` would; and `last_max_rc` plus its drift detection become removable (`account_object.hpp:218`).

## Discrepancies and Potential Issues

1. **KB error — "mana can go negative"** (`reference/rc.md` Mana Regeneration section; Part 08 line 364): RC mana floors at 0 (`manabar.hpp:87-95`, `rc_utility.cpp:585`). Contrib note filed at `contrib/hive-core/2026-06-11-zoom14-rc-mana-floor.md`.
2. **Stale code comment about pending retries**: the long comment in `use_account_rcs` (`rc_utility.cpp:565-573`) argues that transactions losing RC after a new block should be *retried*, "like we currently do" — but commit `26ac90c5d` (2024-10-08) added `is_reapplying_one_tx()` to the throw condition and the corresponding drop in `db_with.hpp:133-136`, so they are now dropped. The comment describes superseded behavior.
3. **`static_assert` message vs condition**: "RC regen time must be smaller than vote regen time" but the assert allows equality (`<=`), and the two are in fact equal (`HIVE_RC_REGEN_TIME = HIVE_VOTING_MANA_REGENERATION_SECONDS`, `config.hpp:481`; `rc_utility.cpp:322-323`). Cosmetic.
4. **Swallowed delegate_rc leaves its differential discount behind**: the evaluator applies the state discount *before* it can fail (`rc_utility.cpp:35`) and adds extra usage only at the end (`:110`); `tx_info` is a plain member of `resource_credits`, not chainbase state, so the nested undo session does not revert it. A `delegate_rc` over existing delegations that fails mid-evaluator in a block leaves a negative `state_bytes` contribution in `tx_info.usage` with no matching positive usage, slightly under-charging the rest of the transaction (floored at 0 per-resource by `prevent_negative`, `resource_count.cpp:599-604,630`). Deterministic on all nodes, cost-only, block-context-only — an accounting quirk, not a divergence risk.
5. **RC counting can throw on the block path for `create_proposal`**: `FC_ASSERT(op.end_date > _now)` in the counting visitor (`resource_count.cpp:488`) runs in `finalize_transaction`, outside any swallow. It is currently unreachable because `create_proposal_evaluator` enforces the identical strict inequality first (`dhf_evaluator.cpp:43`), but the two checks are not visibly coupled; weakening the evaluator check (e.g. to `>=`) would silently turn the RC assert into a block-validity rule.
6. **Mempool livelock for failing delegate_rc**: a pending tx whose `delegate_rc` becomes invalid (e.g. same-amount duplicate after another of the payer's txs landed) is *kept* in mempool — reapplication swallows the failure (not in control), but production throws (in control) and skips it while leaving it pending (`block_producer.cpp:199-207`). It cycles until expiration (max 1 h). Bounded and harmless, but a witness producing under load re-pays the failed-apply cost every block for such txs.
7. **`min_mana` default looks like a bug but is load-bearing**: `std::numeric_limits<uint64_t>::min()` (= 0) as an `int64_t` default strongly suggests an intended `int64_t::min()`; the resulting floor-at-zero is, however, what the rest of the system (and Discovery 2's economics) relies on. Any "fix" to the apparent typo would change behavior.
8. **Build-time float pipeline for baked curve params**: `rc_generate_resource_parameters.py` uses Python floating point (`expm1`, `log`) to produce `coeff_a/b/shift/decay` that end up in state at HF20. Identical released binaries are identical, but independently built binaries depend on the build environment's float behavior for *initial* params (the witness-driven runtime path is integer-only, `rc_curve.cpp`). With RC non-consensus this is cosmetic; under a future RC-consensus hardfork these constants become consensus-critical build artifacts. (The script also emits a `coeff_d` that no C++ struct consumes — dead output.)

## Open Questions

1. **Queen-produced blocks skip production-time RC enforcement**: `block_producer::fill_block_with_transactions` (queen_plugin path, testnet block production) packs pending txs without re-applying them (`block_producer.cpp:218-253`); the block is then applied in the permissive `TX_STATUS_P2P_BLOCK` context. Does queen rely solely on admission-time RC checks, and can a queen testnet therefore mint blocks whose txs exceed payers' RC? (Testnet-only tool — out of this area's scope; colony, the companion load generator, explicitly backs off on `not_enough_rc_exception`, `colony_plugin.cpp:282`.)
2. **Witness-side subsidy print/decay calibration**: how `HIVE_WITNESS_SUBSIDY_BUDGET/DECAY_PERCENT` shape per-witness pools and whether backup witnesses can realistically include subsidized claims — already flagged as a zoom candidate by Part 08; this zoom confirms the consensus asserts but not the economics.
3. **Fork-edge RC accounting for popped transactions**: popped txs re-validate under `TX_STATUS_PENDING` where flood surcharge applies (`rc_utility.cpp:506`) — during a deep fork with a full mempool, formerly-in-block transactions could be dropped purely due to surcharge. Intended?
4. **`rc_stats` stamp as cross-node divergence oracle**: the rolling SHA-256 over payer mana (`rc_objects.cpp:34`, Part 08) would detect shadow-state drift between nodes out-of-band. Is anything operationally comparing these stamps across nodes today?
5. **Exact `is_validating_block` vs `is_replaying_block` boundary** for blocks pushed during sync (P2P but old): which status do sync-applied blocks get, and does it matter for stats accumulation? Both statuses collect stats (`rc_utility.cpp:821`), so RC state is unaffected — but the answer affects log interpretation (`"Accepting transaction"` only fires on `is_processing_block` with HF26, `:564`). Belongs to a block-flow/p2p zoom.
