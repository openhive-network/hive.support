# Findings: rc-consensus

Deep-dive into the boundary between the Resource Credits subsystem and consensus in hive-core at release `1.28.8` (`274384a8adddf54b69965a7fd43d8eb0ddda7701`). Unless a sentence says otherwise, it describes mainnet at 1.28.8, where HF29 is defined in the code but inactive (Part 01, section HF29 (Defined in 1.28.8, Inactive on Mainnet)). Builds on Part 08 (Resource Credits), which covers RC mechanics broadly; this part focuses on *where exactly RC touches consensus*: enforcement contexts, integration points in the transaction/block pipelines, the `delegate_rc` exception-handling machinery, and the determinism discipline that keeps RC state identical across nodes despite not being consensus-enforced.

## Summary

RC at 1.28.8 is "shadow consensus" on mainnet: since the 1.27-era move from a plugin into `libraries/chain/`, all RC state lives in chainbase and is updated by strictly deterministic, block-time-driven code on every node, but until HF29 (see "What it would take to flip the switch") a payer's mana shortfall aborts a transaction only when the node is *in control* (validating a new standalone tx, producing a block) or reapplying pending transactions; during block application and replay the shortfall is merely logged (HF26+) and the payer's mana is floored at zero. Even `delegate_rc` (chain-interpreted since HF26, and whose validity *reads* RC mana state) cannot invalidate a block: `custom_json_evaluator` swallows all interpreter exceptions outside in-control contexts, with a dedicated nested undo session guaranteeing atomic rollback of the failed custom op. Before HF29 the single hard bridge to consensus is the `resource_new_accounts` pool, which is force-overwritten every block with the consensus-enforced `dgpo.available_account_subsidies` value.

## Key Discoveries

### 1. The enforcement decision is a function of six node states, not "mempool vs block"
- **What**: `use_account_rcs` throws `not_enough_rc_exception` iff `db.is_in_control() || db.is_reapplying_one_tx() || db.has_hardfork( HIVE_HARDFORK_1_29_RC_IS_CONSENSUS )` (`rc_utility.cpp:567`; the last term is false on mainnet at 1.28.8, Part 08, "Non-Consensus Status"). `is_in_control()` = `is_validating_one_tx() || is_producing_block()` (`database.hpp:176`), i.e. a new transaction from API or P2P (`TX_STATUS_UNVERIFIED`, `:169`) or the node producing a block (`TX_STATUS_GEN_BLOCK`, `:160`); `is_reapplying_one_tx()` is a pending or popped transaction re-applied outside a block (`TX_STATUS_PENDING`, `:173`). Block application (`TX_STATUS_P2P_BLOCK`, set by `apply_block_extended` for every pushed block, from P2P or the node's own produced block, and for blocks re-applied in a fork switch; `database.cpp:2147`, `database.hpp:156-157`), replay (`TX_STATUS_BLOCK`), and pending reapplication (`TX_STATUS_PENDING`) are *not* in control; before HF29 only the first two of those get the permissive accept-and-log path, while pending reapplication throws.
- **Where**: `libraries/chain/rc/rc_utility.cpp:565-602`, `libraries/chain/include/hive/chain/database.hpp:146-176`
- **Impact**: "RC is enforced at mempool only" is approximately right but loses three distinctions that matter: (a) a node producing a block enforces RC on each transaction it applies while assembling it (`TX_STATUS_GEN_BLOCK`, `block_producer.cpp:149`); (b) pending transactions are re-checked after every block and dropped if they no longer afford (behavior introduced Oct 2024, commit `26ac90c5d`); (c) until HF29 the node applies every block without RC enforcement, whether pushed (`TX_STATUS_P2P_BLOCK`, its own produced block included) or replayed (`TX_STATUS_BLOCK`).

### 2. RC mana cannot go negative — it floors at zero (corrects Part 08 and reference/rc.md)
- **What**: `manabar::use_mana( int64_t mana_used, int64_t min_mana = std::numeric_limits<uint64_t>::min() )`: `uint64_t`'s `min()` is **0**, so the default floor is 0: `current_mana = signed_sat_sub(...); if (current_mana < min_mana) current_mana = min_mana;`. The only RC consumption call is `acc.rc_manabar.use_mana( rc + surcharge )` with the default floor (`rc_utility.cpp:604`). Before HF29 (Part 08, "Non-Consensus Status") a payer included in a block without enough mana ends at exactly 0, not in debt. The delegation paths likewise clamp at 0 (`rc_utility.cpp:401`) or are pre-guarded against negative (`rc_utility.cpp:107-115`).
- **Where**: `libraries/chain/include/hive/chain/util/manabar.hpp:87-95`, `libraries/chain/rc/rc_utility.cpp:604`
- **Impact**: When this part was written, Part 08 (section "Key Properties" under "Mana Bar / Regeneration") and `reference/rc.md` (section "Mana Regeneration") stated that mana can go negative; both were corrected from this finding and now state the zero floor. (Note `std::numeric_limits<uint64_t>::min()` reads like a typo for `int64_t` lowest, but it is load-bearing as a zero floor.)

### 3. delegate_rc failures never invalidate blocks — exception swallowing + nested undo session
- **What**: All `rc_custom_operation` processing runs inside `custom_json_evaluator::do_apply`'s try/catch: `catch (fc::exception) { if (_db.is_in_control()) throw; }`, so outside control an `fc::exception` is silently swallowed, and any other exception is logged and swallowed in every mode (`hive_evaluator.cpp:361-372`; Part 04, section custom_json_evaluator and its Discrepancy 3). Neither catch has a hardfork term. Atomicity of the half-applied custom op is guaranteed by `generic_custom_operation_interpreter::apply_operations`, which opens its own undo session and only `squash()`es on success (`generic_custom_operation_interpreter.hpp:186,224`; the comment in `custom_json_evaluator` cites issue #256, `hive_evaluator.cpp:365-367`).
- **Where**: `libraries/chain/hive_evaluator.cpp:337-373`, `libraries/chain/include/hive/chain/generic_custom_operation_interpreter.hpp:184-251`
- **Impact**: This answers the question Part 08 originally left open (its section "Semantics (HF26+)" under "RC Delegation" now states the outcome): since HF26 the `delegate_rc` evaluator contains unconditional FC_ASSERTs that depend on RC state (insufficient-RC at `rc_utility.cpp:107`, delegate-0-on-create at `:77`, same-amount at `:82`), yet none of them can reject a block, because whenever the node is not in control (block application, replay, pending reapplication) the whole custom op is rolled back and the containing transaction (and its other operations) stands. Through these asserts RC state therefore influences *state evolution* (whether a delegation took effect) but never *block validity*. All nodes still converge because the asserts fire identically everywhere (inputs are deterministic chainbase state).

### 4. Producer/validator symmetry: a generated block is re-applied "as if from P2P"
- **What**: During block production transactions run under `TX_STATUS_GEN_BLOCK` in a throwaway pending session that is reset after assembly (`block_producer.cpp:135-215`); the assembled block is then applied through `database::apply_block_extended`, which unconditionally sets `TX_STATUS_P2P_BLOCK` — "Note that we're treating the block as completely new" (`database.cpp:2140-2147`). RC per-block bookkeeping (`block_info.add`, pending stats) is only accumulated when `is_validating_block() || is_replaying_block()` (`rc_utility.cpp:852-861`), i.e. *not* during generation.
- **Where**: `libraries/chain/database.cpp:2140-2159`, `libraries/plugins/witness/block_producer.cpp:111-216`, `libraries/chain/rc/rc_utility.cpp:852-861`
- **Impact**: Pool levels, usage buckets, weights, and RC stats are derived exclusively from the canonical block-application pass, so the producer and every validator compute identical RC pool state. Without the re-application step, the GEN_BLOCK exclusion would desynchronize the producer's pools from the network.

### 5. The one hard consensus coupling: `resource_new_accounts` pool is slaved to `available_account_subsidies`
- **What**: `finalize_block` computes the new_accounts pool like any other, then discards the result in favor of the consensus value: `new_pool = dgpo.get_available_account_subsidies()` whenever they differ, logging the adjustment (`rc_utility.cpp:801-810`). The consensus pool itself regenerates each block via `rd_apply` in `process_subsidized_accounts` (`database.cpp:1869-1883`) and is decremented by subsidized `claim_account` under *unconditional* consensus asserts: global pool check `hive_evaluator_account.cpp:432-436`, plus elected-witness-only and per-witness pool checks when in a block (`:416-431`).
- **Where**: `libraries/chain/rc/rc_utility.cpp:801-810`, `libraries/chain/hive_evaluator_account.cpp:417-437`, `libraries/chain/database.cpp:1869-1883`
- **Impact**: Subsidized account creation is the only resource where exceeding the budget is a hard block-validity rule — enforced by the consensus twin, not by RC. The RC pool passively mirrors it so RC *pricing* of subsidized accounts tracks the consensus pool level. Witness-voted subsidy params flow in via `rd_setup_dynamics_params` (`witness_schedule.cpp:138-144`) and are pushed into RC params on schedule changes (`witness_schedule.cpp:438` → `set_pool_params`, `rc_utility.cpp:864-882`), regenerating the new_accounts price curve with pure integer math (`rc_curve.cpp:33-99`).

### 6. RC state evolution is deterministic by careful design — a checklist of mechanisms
- **What**: Everything that feeds RC state is consensus-derived: regeneration timestamps use the dgpo `time` (`get_head_block_time()`) or `head_block_time()` (block timestamps, never wall clock, e.g. `rc_utility.cpp:527,57,628`); execution-time costs are fixed benchmark constants compiled in (`operation_exec_info`, `resource_sizes.cpp:167`); state sizes are hardcoded too (with `USE_FIXED_SIZE` defined, object sizes are given values instead of being measured, `resource_sizes.cpp:22-29`); plugin-dependent state (account `json_metadata`) is deliberately *excluded* from both counting and differential discount because its presence depends on the optional `metadata` plugin (`resource_count.cpp:63-65,83-85,205-207`); object-removal batching reads `dgpo.current_remove_threshold`, consensus state, default `HIVE_GLOBAL_REMOVE_THRESHOLD` = 200 (mainnet), settable only by tests (`database.cpp:459-470`, `detail/state/global_property_object.hpp:285`, `protocol/config.hpp:174`); and the witness-driven runtime regeneration of curve params uses integer-only math (`rc_curve.cpp`), unlike the build-time Python float pipeline (`rc_generate_resource_parameters.py`) whose output is frozen into the binary.
- **Where**: as cited per item
- **Impact**: Part 00 (section Notable Findings, finding 1 "Resource Credits Are Non-Consensus", its "Why it exists") states the same: regeneration is lazy but driven entirely by block time, so RC state *is* deterministic across same-binary nodes. The actual obstacles to making RC consensus are different (for how the HF29 switch treats each, see "What it would take to flip the switch"): historical blocks containing RC-violating transactions (replay would fail under retroactive enforcement), cost constants becoming de-facto consensus parameters frozen per-binary, and warning-only invariants that would need to become asserts (the comment under the `FC_TODO` at `rc_utility.cpp:565-566`; the mainnet-build `NOTIFYALERT` wlogs at `:357,393,421`, which assert only under HF29).

### 7. Every consensus path that changes VESTS must bracket the change with RC calls — full inventory
- **What**: The contract is `regenerate_rc_mana(account, now)` *before* the VESTS change and `update_account_after_vest_change(account, now, fill, check_overflow)` *after*; at every site below both calls are made outside any `modify()` of that account. Missed brackets are detected at runtime (Part 08, "Testnet-Only Strict Assertions"): mainnet builds `wlog("NOTIFYALERT! ...")` and assert only under HF29, which a 1.28.8 mainnet build cannot activate; testnet and mirrornet builds (`USE_ALTERNATE_CHAIN_ID`) hard assert (`rc_utility.cpp:344-360,382-396,410-424`). `account_object.last_max_rc` is the stored max RC that the drift check compares against and from which the mana fill after a VESTS change is computed (`rc_utility.cpp:468-487`), commented "for bug catching with RC code, can be removed once RC becomes part of consensus" (`detail/state/account_object.hpp:243`).
- **Where**: call sites: `withdraw_vesting_evaluator` (`hive_evaluator_transfer.cpp:357,399`; `fill=false` so canceling power-down cannot pump mana), `claim_reward_balance_evaluator` (`:699,709`), `delegate_vesting_shares_evaluator` (`:738-739,947-948`, both parties, overflow-checked), `database::adjust_account_vesting_balance` (`database.cpp:1023,1039`, both only when `!is_reward`, i.e. when the VESTS go straight into the vesting balance, for example `transfer_to_vesting` and the producer reward (`database.cpp:1808`, `:1845`), not when they go to the reward balance), `clear_null_account_balance` (`:1239,1248`), `clear_account` (`:1511,1526,1542,1580`, HF23 clears, overflow-checked), `clear_expired_delegations` (`:3162,3170`, returning VEST delegations), `process_vesting_withdrawals` (`database_vesting.cpp:200,211,253,280`, weekly power-down, overflow-checked on the from-account), debug plugin via `update_rc_for_custom_action` (`debug_node_plugin.cpp:354`, `rc_utility.cpp:492-499`).
- **Impact**: This is the maintenance burden RC imposes on consensus code: any new evaluator or per-block process that touches VESTS must add the bracket or it produces NOTIFYALERT drift on mainnet builds (an assertion there only under HF29) and assertion failures on testnet and mirrornet builds. The `_check_for_rc_delegation_overflow=true` variant is required wherever an account can *lose* effective VESTS (power-down, delegation out, account clears), because RC delegations backed by vanished VESTS must be reclaimed (`rc_utility.cpp:426-466`).

### 8. Flood control is a node-local surcharge layer on top of RC, with witness escape hatches at both ends
- **What**: When `_pending_tx_size / dgpo.get_maximum_block_size() > flood_level` (default 20 blocks), new and reapplied transactions pay `surcharge = (blocks_over) * flood_surcharge * cost / 10000` (defaults: `rc_utility.cpp:35-36`; config `rc-flood-level` / `rc-flood-surcharge`, `chain_plugin.cpp:1537-1538,1848-1849`). Computed only when `is_validating_one_tx() || is_reapplying_one_tx()` (`rc_utility.cpp:530`), never part of block-context accounting. Single-op transactions (the op tag is recorded only for one-operation transactions, `rc_utility.cpp:888-889`) carrying `feed_publish` / `witness_update` / `witness_set_properties` whose payer's witness object has `schedule == witness_object::elected` are exempt (the check runs only while the mempool is over the flood level, `:538-551`) and additionally marked privileged (`full_transaction.hpp:91,132`); when the node accepts such a transaction as new (`is_validating_one_tx()`), the mark puts it at the *front* of the pending list via the fork-recovery `_popped_tx` mechanism, while a re-applied one goes to the back like any other (`database.cpp:648-656`).
- **Where**: `libraries/chain/rc/rc_utility.cpp:529-562`, `libraries/chain/database.cpp:648-653`, `libraries/plugins/chain/chain_plugin.cpp:1533-1538`
- **Impact**: Two nodes with different flood settings can legitimately disagree about mempool admission; this is fine because the surcharge is computed only for new and re-applied pending transactions, never on the block path (`rc_utility.cpp:530`). Witness ops stay deliverable under flood both by being surcharge-exempt and by jumping the queue, so the chain can raise `maximum_block_size` (or fix feeds) to resolve congestion. Pending transactions that can no longer pay (base or surcharged) are dropped at reapplication (`db_with.hpp:133-136`, counted as `failed_txs`); mempool is additionally bounded by `max-mempool-size` (default 100M, `chain_plugin.cpp:1536`): after a block, pending transactions are re-applied for at most 200 ms (`HIVE_PENDING_TRANSACTION_EXECUTION_LIMIT`, `protocol/config.hpp:422`, `db_with.hpp:108-110`), and the rest are kept without re-application while the mempool is below `max-mempool-size` and dropped beyond it (`db_with.hpp:156-171`).

### 9. Custom-op parsing is two-mode: strict for in-control, lenient for blocks
- **What**: `custom_json_operation.json` for id `"rc"` is parsed with `format_validation_mode::full` when in control, `relaxed` otherwise (`generic_custom_operation_interpreter.hpp:231`); UTF-8 truncation verification is disabled outside control (`hive_evaluator.cpp:353-357`). Structurally wrong-but-parseable variants (array size != 2, extra fields) assert only in control; outside control (blocks, replay, pending reapplication) they log "Incomplete/Dangling custom operation ignored" and proceed with whatever parsed (`generic_custom_operation_interpreter.hpp:88-125`). Inner ops are `validate()`d and must require *exactly* the same authority sets as the outer custom_json (`:200-211`), all inside the swallowed-exception zone.
- **Where**: `libraries/chain/include/hive/chain/generic_custom_operation_interpreter.hpp:59-143,184-251`
- **Impact**: A malformed `"rc"` custom_json is rejected at the API/mempool boundary but tolerated (as a no-op) inside a block — the same asymmetric philosophy as mana enforcement, applied at the parse layer. This is what makes it safe for the chain to interpret a custom_json id at all without a hardfork-style validity cliff.

### 10. HF26 turned `delegate_rc` from dead letter to active, with a deliberate one-sided gate
- **What**: Pre-HF26 the evaluator returns early (`dlog "Ineffective RC delegation"`, `rc_utility.cpp:40-44`): the op parses, costs custom_json RC, but does nothing. Post-HF26 it executes; its `is_in_control()`-gated asserts (minimum delegation = `account_creation_fee/3` in VESTS `:49-55`; no `delegate_rc` at all from an account whose expired-delegation cleanup is pending `:60`) are policy-only, while its unconditional asserts (`:77,82,107`) are state-integrity rules that, per Discovery 3, still cannot break blocks. The extra RC usage of the inner op is collected by the evaluator itself (`handle_custom_op_usage`, `:121`; `resource_count.cpp:672-678`) because by `finalize_transaction` time the JSON would otherwise need re-interpretation.
- **Where**: `libraries/chain/rc/rc_utility.cpp:38-122`
- **Impact**: The HF26 gate is the template for chain-interpreting custom ops: hardfork-gate the *effect*, never the *parseability*, and keep every failure swallowed outside control. Note there was no HF26 state migration for RC delegations (the HF26 case of `apply_hardfork`, `database_hardfork.cpp:491-504`, only sets the HBD stop/start percents and creates the future witness schedule object): the delegation indices simply start empty.

## The RC↔Consensus boundary in detail

### Node-state predicates and what RC does in each

`database.hpp:146-176` defines the state lattice (`TX_STATUS_*`); RC behavior keyed to it:

| Context | Predicate | `use_account_rcs` on shortfall | Flood surcharge | `delegate_rc` failure | RC stats/`block_info` |
|---|---|---|---|---|---|
| New tx from API/P2P | `is_validating_one_tx()` (in control) | throw `not_enough_rc_exception` → tx rejected | yes | throws → tx rejected | not collected |
| Reapplying pending after block/fork | `is_reapplying_one_tx()` | throw → tx **dropped** from mempool (`db_with.hpp:133-136`) | yes | swallowed → tx survives, delegation skipped | not collected |
| Producing a block | `is_producing_block()` (in control) | throw → tx skipped, stays pending (`block_producer.cpp:199-207`) | no | throws → tx skipped, stays pending | not collected |
| Validating block from P2P (incl. own generated, forks) | `is_validating_block()` | until HF29: accept; `ilog "Accepting transaction..."` if HF26 (`rc_utility.cpp:584-601`); mana floored at 0. Under HF29: throw, the block fails to apply (see "What it would take to flip the switch") | no | swallowed, rolled back | collected |
| Replaying irreversible blocks | `is_replaying_block()` | until HF29: accept; same log path. Under HF29: throw, as above | no | swallowed, rolled back | collected |

Mempool-shortfall messages distinguish the surcharge case: if base cost is affordable but cost+surcharge is not, the error tells the user to wait / power up / ask witnesses for bigger blocks (`rc_utility.cpp:569-576`).

A payer-less transaction (no operation yields a payer, see below) fails when the node is in control and, under HF29, in every context (see "What it would take to flip the switch"); otherwise it is applied without charging anyone (`rc_utility.cpp:503-510`; an `FC_ASSERT` since 1.28.8, at 1.28.7 a `plugin_exception` thrown only in control). Payer resolution takes the first operation that yields a payer: `witness_set_properties` (owner), `recover_account` (account_to_recover) and `witness_block_approve` (witness) are explicit overrides, any other operation yields the first account of its required active, else owner, else posting authorities (`resource_user.cpp:11-65`).

### Transaction pipeline integration

Order inside `database::_apply_transaction` (`database.cpp:2661-2719`):

1. `notify_pre_apply_transaction`, then `rc().reset_tx_info(trx)` (`database.cpp:2705-2706`): zeroes `tx_info`, resolves payer, records single-op tag (`rc_utility.cpp:884-890`).
2. Per operation, `database_impl::apply_operation` (`database.cpp:2739-2763`): if HF20+, `rc().handle_operation_discount<operation>(op)` *before* the evaluator (`database.cpp:2754-2755`): accumulates negative `state_bytes` usage for state about to be replaced (account authority updates, witness updates, recover_account; `resource_count.cpp:17-168`). For `delegate_rc`, the evaluator itself reports the discount for existing rc delegations and the extra usage (`rc_utility.cpp:46,121`).
3. After all ops, `rc().finalize_transaction(full_tx)` (`database.cpp:2716`, HF20-gated at `rc_utility.cpp:832`): `count_resources` over the signed tx (sizes, expiration-scaled tx base, signature-scaled verify time; `resource_count.cpp:582-631`), `compute_cost` (per-resource price curve over current pools; `rc_utility.cpp:299-329`), `full_tx.set_rc_cost(total)`, then `use_account_rcs(total)` which regenerates and debits the payer; privileged status propagates to `full_tx.set_privilege()` (`rc_utility.cpp:844-850`).
4. Only when validating/replaying a block: `block_info.add(tx_info)` and pending-stats accumulation (`rc_utility.cpp:852-861`).

Note `finalize_transaction` runs *inside* the transaction's `FC_CAPTURE_AND_RETHROW`: an exception here fails the transaction, and in a block context would fail the **block**. The following checks are kept off the block path or pre-guarded: the surcharge overflow assert sits behind the mempool-only branch (`rc_utility.cpp:530,558`), `compute_cost`'s `FC_ASSERT(rc_regen > 0)` is pre-guarded by the caller (`:270,311,320`), and `FC_ASSERT(op.end_date > _now)` for `create_proposal` in the counting visitor (`resource_count.cpp:488`) is preceded by the DHF evaluator's identical strict check earlier in the same transaction (`dhf_evaluator.cpp:42`). See Discrepancies #5. Under HF29 the balance and missing-payer checks of `use_account_rcs` assert on the block path too (see "What it would take to flip the switch").

### Block pipeline integration

Order inside `database::_apply_block` (`database.cpp:2200-2386`):

1. `rc().reset_block_info()` immediately after `notify_pre_apply_block` (`database.cpp:2207-2208`).
2. Transactions apply (accumulating `block_info` per above, `database.cpp:2309-2319`), then the head-block updates and the per-block processes (`database.cpp:2331-2368`), then RC's two block-level steps right before `process_hardforks()` (`database.cpp:2373`):
   - `rc().handle_expired_delegations()` (`database.cpp:2370`; `rc_utility.cpp:617-656`, HF26-gated): continues clearing RC-delegation overflow that VEST changes in earlier blocks or earlier in this block could not finish, oldest `rc_expired_delegation_object` first, with one `remove_guard(get_remove_threshold())` for this end-of-block step, while each VEST change earlier in the block has its own (`rc_utility.cpp:436-438`; Part 08, "Delegation Overflow").
   - `rc().finalize_block()` (`database.cpp:2371`; `rc_utility.cpp:765-828`, HF20-gated): per resource: record budget, `decay = rd_compute_pool_decay(params.decay_params, pool - usage, 1)` (decay applies to the post-usage pool), add the block's usage to the 24h window sum, first subtracting the usage of the oldest of the 24 x 1h buckets when it is due for reuse (`HIVE_RC_BUCKET_TIME_LENGTH`/`HIVE_RC_WINDOW_BUCKET_COUNT`, `protocol/config.hpp:482-483`; `rc_utility.cpp:795-797`), `new_pool = pool - decay + budget - usage`, new_accounts pool overwritten from consensus (Discovery 5), the result clamped at >= 0; then `recalculate_resource_weights` (`rc_objects.hpp:81-95`) and the daily stats rotation/report (`handle_auto_report`, `rc_utility.cpp:698-746`: since 1.28.8 `finalize_stats` closes the pending stamp, the report is emitted, `archive_stats` copies the pending object into the archive and `reset_stats` restarts the pending one, `:704-708`, `:737-745`, where 1.28.7 had a single `archive_and_reset_stats`; frequency `HIVE_RC_STATS_REPORT_FREQUENCY`, which is `HIVE_BLOCKS_PER_DAY` on mainnet, `protocol/config.hpp:486-488`); last, the block's usage is added to the active bucket, which is first reset to the block time when it is the reused oldest one (`rc_utility.cpp:821-827`).
3. RC state participates in the block's undo session like all chainbase state (`apply_block_extended`, `database.cpp:2149-2158`), so fork switches rewind RC state consistently — including across the fork boundary, since popped blocks' transactions land in `_popped_tx` and re-validate under `TX_STATUS_PENDING`.

### HF20 genesis of RC state

`database_hardfork.cpp:361-409` (inside `case HIVE_HARDFORK_0_20`, `database_hardfork.cpp:331-412`): params loaded from the build-time-compiled jsonball (`hive::jsonball::get_resource_parameters()`, `database_hardfork.cpp:364`; source `libraries/jsonball/data/resource_parameters.json`, transform `programs/build_helpers/hive_build_helpers/rc_generate_resource_parameters.py`, wiring `libraries/jsonball/CMakeLists.txt:28-30`); new_accounts params immediately overridden from the witness schedule (`set_pool_params`, `database_hardfork.cpp:381`); 24 buckets created with back-dated timestamps (`database_hardfork.cpp:384-390`); pools start at `pool_eq` (`database_hardfork.cpp:392`, `rc_objects.hpp:48-59`); pending+archive stats objects created (`database_hardfork.cpp:395-396`); every existing account gets `rc_adjustment = HIVE_RC_HISTORICAL_ACCOUNT_CREATION_ADJUSTMENT` (2020748973, i.e. 2020.748973 VESTS, which the code comment equates with 1.000 HIVE at HF20 on mainnet, `protocol/config.hpp:491`) and a full mana bar (`database_hardfork.cpp:398-409`). Post-HF20 accounts get `rc_adjustment` = the creation fee passed to `create_account` times the vesting share price at creation (`hive_evaluator_account.cpp:144-153`); that fee is the median `account_creation_fee`, which `account_create` must pay exactly (`hive_evaluator_account.cpp:166-170`) and which `create_claimed_account` passes as well (`hive_evaluator_account.cpp:473-474`). The custom-op interpreter for `"rc"` is registered unconditionally at database open (`database_init.cpp:38` -> `rc_utility.cpp:748-763`), so even pre-HF26 blocks parse `"rc"` custom_jsons (leniently, per Discovery 9).

### What it would take to flip the switch

Since 1.28.8 the switch is in the code: `HIVE_HARDFORK_1_29_RC_IS_CONSENSUS`, defined as `(HIVE_HARDFORK_1_29)` with the comment "RC is part of consensus" (`hardfork.d/1_29.hf:27-28`). Under it the RC payer and balance checks assert in every mode, which makes RC part of consensus; before HF29 they assert only when the node is in control, the balance check also when it re-applies its pending transactions (Part 01, section HF29 (Defined in 1.28.8, Inactive on Mainnet); Part 08, "Non-Consensus Status"). HF29 is defined in 1.28.8 code and inactive on mainnet, and a 1.28.8 mainnet build cannot activate it: `HIVE_NUM_HARDFORKS` is 28 in mainnet builds and 29 only with `USE_ALTERNATE_CHAIN_ID`, i.e. in testnet and mirrornet builds (`hardfork.d/0-preamble.hf:15-20`, `cmake/hive_options.cmake:31-35`), only those builds register HF29 (`database_hardfork.cpp:112-116`), and `process_hardforks()` applies the next hardfork only if `last_hardfork < HIVE_NUM_HARDFORKS` (`database_hardfork.cpp:131-133`). The switch has five sites, all in `rc_utility.cpp`: the balance check in `use_account_rcs`, `if( db.is_in_control() || db.is_reapplying_one_tx() || db.has_hardfork( HIVE_HARDFORK_1_29_RC_IS_CONSENSUS ) )` (`rc_utility.cpp:567`); the missing-payer check `FC_ASSERT( !db.is_in_control() && !db.has_hardfork( HIVE_HARDFORK_1_29_RC_IS_CONSENSUS ), "Tried to execute transaction with no resource user" )` (`:507-508`); and the three invariant checks of mainnet builds (max RC drift `:354`, missing regeneration before an RC delegation change `:391`, missing regeneration before a VEST change `:419`), which mainnet builds log as `NOTIFYALERT` and assert only under HF29, while testnet and mirrornet builds assert them unconditionally (`:350`, `:388`, `:416`; Part 08, "Testnet-Only Strict Assertions").

The code comments at these sites read as follows. The balance check carries `FC_TODO( "Leave only hardfork condition after it triggers" ); //we might want to activate consensus retroactively (HF27 perhaps?) - test it once HF29 triggers` and, on the next line, `//we should also replace all NOTIFYALERT warnings in RC with assertions, since they can't ever happen` (`rc_utility.cpp:565-566`); at 1.28.7 that `FC_TODO` read `"Add || db.has_hardfork( X ) to make RC part of consensus since X"`. The other four sites carry `FC_TODO( "Make it an unconditional assertion after HF29" ); // <- needs to be checked with replay` (`:348`, `:386`, `:414`, `:506`).

What the 1.28.8 code does for each prerequisite visible from this zoom (Discovery 6 names the obstacles): the gate is `has_hardfork`, true once the hardfork has been processed (`database_hardfork.cpp:151-154`), so blocks applied before the hardfork, in a replay too, keep the permissive path. Under HF29 the balance check asserts for each transaction of a block too (it is reached from `finalize_transaction`, `rc_utility.cpp:849`), and a failing transaction fails the whole block (`database.cpp:2309-2319`). The flood surcharge is still computed only for new and re-applied pending transactions (`rc_utility.cpp:530`), so it never enters the block-path check. The compiled-in cost constants (`resource_sizes.cpp`: the state sizes, fixed by `USE_FIXED_SIZE` at `:26-29`, and the execution times from `:167`) have no HF29 term; under HF29 the cost computed from them (`count_resources`, `compute_cost`) is what the balance check compares on the block path. The `custom_json_evaluator` catches have no HF29 term either (`hive_evaluator.cpp:361-372`), so under HF29 a failing `delegate_rc` still does not fail a block (Discovery 3); the transaction-level checks in `use_account_rcs` run outside that catch. `last_max_rc` and its code comment "(for bug catching with RC code, can be removed once RC becomes part of consensus)" are unchanged (`detail/state/account_object.hpp:243`); its drift check is the first of the three invariant checks above.

## Discrepancies and Potential Issues

1. **KB error, since corrected: "mana can go negative"**: when this part was written, `reference/rc.md` (section "Mana Regeneration") and Part 08 (section "Key Properties" under "Mana Bar / Regeneration") said RC mana can go negative, while it floors at 0 (`manabar.hpp:87-95`, `rc_utility.cpp:604`). Both were corrected from this finding (producer commit `bccdfd24b`, which also digested the contrib note) and now state the zero floor.
2. **Stale code comment about pending retries**: the long comment in `use_account_rcs` (`rc_utility.cpp:586-593`) argues that transactions losing RC after a new block should be *retried*, "like we currently do"; but commit `26ac90c5d` (2024-10-08) added `is_reapplying_one_tx()` to the throw condition and the corresponding drop in `db_with.hpp:133-136`, so at 1.28.8, as at 1.28.7, they are dropped. The comment, unchanged at 1.28.8, describes superseded behavior.
3. **`static_assert` message vs condition**: "RC regen time must be smaller than vote regen time" but the assert allows equality (`<=`), and the two are in fact equal (`HIVE_RC_REGEN_TIME = HIVE_VOTING_MANA_REGENERATION_SECONDS`, `protocol/config.hpp:480`; `rc_utility.cpp:335-336`). Cosmetic.
4. **Swallowed delegate_rc leaves its differential discount behind**: the evaluator applies the state discount *before* it can fail (`rc_utility.cpp:46`) and adds extra usage only at the end (`:121`); `tx_info` is a plain member of `resource_credits`, not chainbase state, so the nested undo session does not revert it. A `delegate_rc` over existing delegations that fails mid-evaluator when the node is not in control (block application, replay, pending reapplication) leaves a negative `state_bytes` contribution in `tx_info.usage` with no matching positive usage, slightly under-charging the rest of the transaction (floored at 0 per-resource by `prevent_negative`, `resource_count.cpp:599-604,630`). Deterministic on all nodes, cost-only, limited to the contexts that swallow the failure: an accounting quirk, not a divergence risk.
5. **RC counting can throw on the block path for `create_proposal`**: `FC_ASSERT(op.end_date > _now)` in the counting visitor (`resource_count.cpp:488`) runs in `finalize_transaction`, outside any swallow. At 1.28.8 it is unreachable because `create_proposal_evaluator` enforces the identical strict inequality first (`dhf_evaluator.cpp:42`), but the two checks are not visibly coupled; weakening the evaluator check (e.g. to `>=`) would silently turn the RC assert into a block-validity rule.
6. **Mempool livelock for failing delegate_rc**: a pending tx whose `delegate_rc` becomes invalid (e.g. same-amount duplicate after another of the payer's txs landed) is *kept* in mempool — reapplication swallows the failure (not in control), but production throws (in control) and skips it while leaving it pending (`block_producer.cpp:199-207`). It cycles until expiration (max 1 h). Bounded and harmless, but a witness producing under load re-pays the failed-apply cost every block for such txs.
7. **`min_mana` default looks like a bug but is load-bearing**: `std::numeric_limits<uint64_t>::min()` (= 0) as an `int64_t` default strongly suggests an intended `int64_t::min()`; the resulting floor-at-zero is, however, what the rest of the system relies on (Discovery 2). Any "fix" to the apparent typo would change behavior.
8. **Build-time float pipeline for baked curve params**: `rc_generate_resource_parameters.py` uses Python floating point (`expm1`, `log`) to produce `coeff_a/b/shift/decay` that end up in state at HF20. Identical released binaries are identical, but independently built binaries depend on the build environment's float behavior for *initial* params (the witness-driven runtime path is integer-only, `rc_curve.cpp`). Until HF29 this is cosmetic; under HF29 the costs computed from these params enter the block-path balance check (see "What it would take to flip the switch"). (The script also emits a `coeff_d` that no C++ struct consumes: dead output.)

## Open Questions

1. **Queen-produced blocks skip production-time RC enforcement** (settled from the 1.28.8 code): when the flow control's `skip_transaction_reapplication()` is true (the queen plugin's, `queen_plugin.cpp:81`; since 1.28.8 also the debug plugin's with `debug_generate_blocks(..., skip_tx_reapplication = true)`, a C++ call used by unit tests through `generate_block_from_pending()`, `debug_node_plugin.cpp:44`, `:362-363`, `database_fixture.cpp:144`), `block_producer` calls `fill_block_with_transactions`, which packs pending txs without applying them (`block_producer.cpp:55-58`, `:218-253`), so no RC check runs at production. The block is then applied as `TX_STATUS_P2P_BLOCK` (`database.cpp:2147`): until HF29 a shortfall there is logged and the mana floored at 0, under HF29 it fails the block (see "What it would take to flip the switch"). Before that, RC is checked for such transactions only when they enter pending (`TX_STATUS_UNVERIFIED`, in control) and when pending transactions are reapplied (`TX_STATUS_PENDING`); `debug_push_pending_transaction` puts a transaction into pending without evaluating it (`debug_node_plugin.cpp:179-203`). (Test tools: queen and colony refuse to initialize in mainnet builds, `queen_plugin.cpp:273-274`, `colony_plugin.cpp:887-888`; colony, the companion load generator, catches `not_enough_rc_exception` on its own transactions and only counts it, `colony_plugin.cpp:282`.)
2. **Witness-side subsidy print/decay calibration**: how `HIVE_WITNESS_SUBSIDY_BUDGET/DECAY_PERCENT` shape per-witness pools and whether backup witnesses can realistically include subsidized claims: already flagged as a zoom candidate by Part 08, whose section "Out-of-Scope / Zoom Candidates" (item 1) now points to Part 17 (witness-subsidy), Key Discoveries 1-5; this zoom confirms the consensus asserts but not the economics.
3. **Fork-edge RC accounting for popped transactions**: popped txs re-validate under `TX_STATUS_PENDING` where flood surcharge applies (`rc_utility.cpp:530`) — during a deep fork with a full mempool, formerly-in-block transactions could be dropped purely due to surcharge. Intended?
4. **`rc_stats` stamp as cross-node divergence oracle**: the rolling SHA-256 over payer mana (`rc_objects.cpp:32`, Part 08) would detect shadow-state drift between nodes out-of-band. Is anything operationally comparing these stamps across nodes today? Still open at 1.28.8; since 1.28.8 `rc-stats-report-output=JSONL` appends each periodic report, `stamp` included, as one JSON line to `rc_stats.jsonl`, a relative path, so in the node's working directory (`rc_utility.cpp:25-29`, `:164`, `:724-730`), which makes the stamps machine-collectable.
5. **Exact `is_validating_block` vs `is_replaying_block` boundary** for blocks pushed during sync (P2P but old), settled from the code: a block from P2P, during sync as in live mode, goes through `chain_plugin::accept_block` and the write queue to `push_block` (`p2p_plugin.cpp:170`, `chain_plugin.cpp:348`, `:1101`), whose `_push_block` applies it with `apply_block_extended` (`chain_plugin.cpp:1141`), which sets `TX_STATUS_P2P_BLOCK` (`database.cpp:2147`): sync-applied blocks are `is_validating_block()`. Only replay from the local block log (`reindex_internal`) sets `TX_STATUS_BLOCK` (`chain_plugin.cpp:1279`) and applies with `db.apply_block` (`:1296`). Both statuses collect stats (`rc_utility.cpp:852`), so RC state is unaffected, and both are `is_processing_block()`, so until HF29 the `"Accepting transaction"` log (HF26+, `:584`) fires in both.
